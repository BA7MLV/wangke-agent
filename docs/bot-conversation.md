# Bot 分段消息

参考 nanobot 的 `MessageTool`：发送消息是独立的工具动作，不必与结束当前轮次绑定。消息发送到当前会话，经现有消息事件链路同步到 Web 和已绑定的 IM。

- `send_message({ kind: "text", text: "先说结论…", complete: false })`：立即发送一条普通聊天消息，继续执行。可在多个工具步骤之间调用，也可在同一个工具批次中按顺序调用。
- `study_send_file({ fileId, caption: "这张图更直观" })`：发送一张已有图片或一个已有文件，可带说明，继续执行。文件类型不限制为学习资料；需要真实的、属于当前用户的文件 ID，沿用文件读取权限。
- `send_message({ kind: "text", text: "最后补充…", complete: true })`：发送最后一条消息并结束。省略 `complete` 保留旧行为，避免已有任务无法结束。
- `finish_turn({})`：已有消息或附件发出后直接结束，不再重复发送总结。没有发送过有效回复时会要求先回复。

模型按语义自然分段，简短回答保留为一条消息；不机械拆开每句话，不用进度消息代替聊天。最后一个结束动作必须排在其他待执行动作之后。`question` 仍结束当前轮等待用户输入，`approval` 仍进入审批流程，`progress` 始终继续。

附件必须通过文件工具发送，不能把文件 JSON 塞进普通消息来绕过权限。发送成功表示已写入会话，外部 IM 的实际送达仍由网关负责。

验证：`npx tsx scripts/test-bot-conversation.mjs`。

## 微信整批读图

微信图片消息进入同一个任务后，运行时先用 `study_file` 读取当前输入的全部图片，再进入回答阶段。每轮最多安排 16 个读图工具调用，沿用已有工具执行器的有界并发、权限审批和预算；每张图的视觉结果持久化，暂停或重启不重读已成功的图片。汇总请求按原始图序携带全部视觉结果，并纳入上下文用量估算。空结果、截断或读取失败不会直接生成部分答案。普通聊天回复及文件发布都发生在这道读图完成检查之后。

接收端允许一条消息包含最多 99 个附件，不再按 8 张或固定 8 秒强制拆成多个任务。跨平台消息的批次边界仍按到达间隔推断，能力边界及协议来源见 [连续图片合并](im-gateway.md#连续图片合并)。验证：`npm run test:gateway`。

## 微信公式格式

微信 ClawBot 的 Markdown/代码块能力不代表支持 LaTeX 排版。运行时每轮从有效的 iLink 绑定加载渠道要求（也覆盖恢复中的旧任务）：聊天直接使用可读的线性表达式和 Unicode，例如 `(a+b)/(c+d)`、`x²`、`√(x+1)`；需要推导时保留括号、上下限、单位等必要信息。Web 独立线程不受此限制。

发布普通回复、`send_message` 或文件说明前，检查代码/URL 之外的公式定界符与常见 TeX 命令。如果仍是公式源码，本次模型响应不发布、该响应的工具批次不执行，向模型返回格式修正要求。最多修正两次，次数按 run 持久化并计入正常用量/步骤预算；仍失败时明确提示格式处理失败，不把残缺或生硬删除命令后的公式当成答案。以前成功执行的操作不重跑，已发送消息不撤回。明确展示源码的代码块保留原样。

这不是 LaTeX 图片渲染器，也不会重写已投递的消息或旧 outbox；模型对复杂公式改写的准确性仍需实际样例验收。验证：`npm run test:gateway:chunking`，包含三种模型协议的直接回复、消息工具、重启修正预算及 Gateway 投递回归（模型/传输模拟）。
