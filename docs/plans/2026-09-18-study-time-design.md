# 学习时长（在线时长 + GitHub 提交图）设计：可见且在场才计时，一天一行

- 状态：**已实现并回归**（DB v11）
- 日期：2026-09-18
- 需求：记录每天学了多久（在线时长），并用 GitHub 提交图那样的热力图展示

## 1. 需求拆解：三个问题必须先答清楚

「记录学习时长」听着是一件事，落地要先把三个判断标准定死，否则做出来的数字没人信：

| 问题 | 决定 | 理由 |
| --- | --- | --- |
| 什么算「在线」？ | 页面在前台（`visibilityState === 'visible'`） | 切到别的标签页、锁屏、PWA 收后台都不算。这是最没有争议的一半 |
| 什么算「在场」？ | 默认 5 分钟内有过输入（指针/键盘/滚轮） | 页面开着人走开是最常见的「假在线」。阈值可调（2/5/10/15 分钟） |
| **看视频时人根本不动键鼠，怎么办？** | **正在播放视频时不判空闲** | 这条是必需的，不是优化：看两小时网课本就不需要操作，按「有操作才算」会把最核心的场景全记成 0 |

第三条是这次设计里唯一的「领域判断」：通用在线时长统计（网页分析工具那一类）不需要它，
而学习应用必须要有 —— 所以播放页会上报播放态（`setStudyMediaPlaying`），
暂停/播完/离开播放页即恢复普通空闲判定。

## 2. 不变量

1. **只增不减**。任何一次心跳只往当天加秒数，不做减法（清空记录是显式操作）。
2. **不记错账**。跨零点的那次心跳按本地零点切成两天，不能整段记在今天或明天。
3. **记时长的代码不能把应用搞崩**。落库失败（配额满/库被关）只留内存里下次再试，
   绝不抛到 UI；`visibilitychange` / `pagehide` 上也只做「尽力而为」的补落。
4. **不为了计时写爆存储**。15 秒一次心跳，但 1 分钟才落一次库。
5. **不污染其它数据**。清空学习记录只清 `studyDays`。

## 3. 设计

### 3.1 数据层（v11）：一天一行，主键就是日期

```ts
export interface StudyDayRow {
  date: string;    // 主键：本地日期 YYYY-MM-DD
  seconds: number; // 当日累计秒数
  updatedAt: number;
}
```

- **为什么主键用日期字符串**：热力图是「按区间取一段」，字符串主键上 `between(a, b)`
  就是天然有序的范围查询；用自增 id 还得再建索引。一天一行的语义下，
  「今天那行」的 upsert 天然幂等。
- **为什么不放 localStorage**：一天一行、一年 365 行，这是**数据**不是**配置**；
  localStorage 只有几 MB 且同步写，放久了拖慢启动。
- 读的时候整表 `toArray()`（一天一行两个数字，十年也只有 3650 行）—— 比
  「按区间查 + 另开一条总账查询」简单得多，统计（累计/最长连续）本来就要全量。

### 3.2 纯逻辑（`utils/studyLog.ts`）：日期与几何

单独拆出来的原因：这一段最容易错的全部在「日期」上，而它们都能用纯函数表达并单测
（`scripts/test-study-log.mjs`，21 项）：

- `dateKey` 用**本地**日期。⚠️ 不能用 `toISOString().slice(0,10)` —— 那是 UTC 日期，
  东八区在本地 00:00~08:00 之间会把记录算到**前一天**（凌晨学习的人会看到
  「今天没记上、昨天莫名多了一截」）。
- `splitByDay(from, to)`：按本地零点切分。23:59:50 → 00:00:05 的 15 秒，
  10 秒记今天、5 秒记明天。
- `buildHeatmap`：列 = 周（周日打头）、行 = 周日…周六，最后一列是本周，
  本周里晚于今天的格子标 `future`（只占位不画）。月份标签落在**含「1 号」的那一列**上
  （GitHub 就是这么标的）；首列若离第一个标签太远，补一个首列所属月份的标签。
- `heatLevel`：**固定阈值** 15 / 45 / 90 分钟分四档。
  为什么不用 GitHub 那种「按本人历史取四分位」：四分位会把**任何**数据染成满格 ——
  一个每天学 5 分钟的人，5 分钟那天也是最深的一档，看着像天天学满 8 小时。
  这张图是给自己看进度的，绝对刻度更诚实，图例里也把三档写出来。
- `computeStats`：累计 / 活跃天 / 今日 / 近 7 天 / 窗口内活跃天 / 当前连续 / 最长连续 / 最佳单日 / 全期日均。
  当前连续按「还活着」算：今天有记录从今天往回数；今天还没开始、但昨天有，就从昨天数
  （今天才刚开始学的人不该看到连续天数先归零再涨回来）。
  **日均与「近 7 天」不是一套口径**：`averageSeconds` 是 `totalSeconds / activeDays`（全期），
  所以它只挂在「累计学习」卡上；「近 7 天」卡要报日均，分母只能用窗口内的 `weekActiveDays`
  或固定 7 天。两个口径混用会得到「标题说 7 天、数字是全期」的错位文案 ——
  这个 bug 真出现过（见 §5 第 5 条），现在由单测与 e2e 各钉一条断言。

### 3.3 追踪器（`store/studyTime.ts`）：15 秒心跳 + 内存缓冲

```
setInterval(15s)
  → shouldCount(now) ?  可见 且（播放中 或 距上次操作 < 空闲阈值）
  → splitByDay(上次心跳, now) 累加进内存 pending（按日期）
  → 每 4 次心跳（1 分钟）落一次库；页面隐藏 / 卸载时补落一次
```

四个细节各有原因：

1. **单次心跳最多计入 30 秒**（`MAX_TICK_MS = 2 × TICK_MS`）。设备睡眠 / 系统挂起时
   定时器根本不触发，醒来后 `now - lastTick` 可能是几小时 —— 那几个小时人不在，
   不能算学习。截断到两个心跳周期：正常节流不被误伤，真睡过去的时间也不会被补记。
2. **无论计不计时都推进 `lastTick`**。不推进的话「空闲一段后再回来」会把整段空闲补记进去。
3. **落库成功后才从 pending 里扣掉**。写入期间的增量要留着，否则 UI 上的「今日」会先掉一下再涨回来。
4. **值没变就不 setState**。心跳很密，别让无关组件跟着重渲染。

发布出去的 `pending` 让页面能显示**此刻**的今日时长（而不是滞后一分钟的库值）：
`库里的记录 + 内存 pending` 叠加后才是「今天」。

### 3.4 播放态豁免（`pages/Player.tsx`）

`onPlay` / `onPlaying` → 计时豁免；`onPause` / `onEnded` → 恢复；
**离开播放页（或换视频）时在 `id` 的依赖上清一次** —— 不清的后果很具体：
从播放页返回课程库后标记还是 true，人去吃饭了库页照样一直记时长。

### 3.5 页面（`pages/Study.tsx` + `study.css`）

- 4 张统计卡（累计 / 今日 / 近 7 天 / 连续天数），「今日」卡带一个呼吸点表示正在计时。
  「累计学习」的副文案是 `活跃 N 天 · 日均 X`（全期口径），「近 7 天」只报窗口内活跃天数 ——
  日均挂哪张卡见 §3.2 的口径说明。副文案拆成片段做 `inline-flex` 换行，
  否则 390px 下会把「1 小时 05 分」从中间掰开、折出末尾孤零零一个「分」字。
- 热力图：53 周 × 7 行（11px 格 + 3px 间距 = 14px 步距），横向滚动、默认停在本周；
  悬浮或点按出提示条（时长 + 「今天 · 2026-09-18」）；图例 5 档 + 档位文字说明；
  今天的格子描一圈主色。区间可切近 3 个月 / 近半年 / 近一年（列数 14 / 27 / 53）。
- 最近 30 天明细：条形按这 30 天的最大值归一，颜色仍用热力档位，方便核对图上的颜色。
- **配色用 GitHub 那套绿**（浅色 #9be9a8→#216e39、深色 #0e4429→#39d353），
  而不是 MD3 的 primary 四档透明度：需求原话是「像 GitHub 提交那样」，**认得出**是这件事
  的全部意义；只有「空格子」用主题的 surface 令牌，深浅两种主题下都不打架。
- 事件委托：提示条用容器上的 `onMouseOver` / `onClick`，不给 371 个格子各挂一个处理器。
  坐标按「格子相对滚动容器」算，提示条是滚动容器的绝对定位子元素，横向滚动时跟着走。

### 3.6 设置页（`components/StudyTimeCard.tsx`）

自动记录开关 / 空闲判定档位 / 已有记录摘要 + 清空记录（带确认弹窗）。

### 3.7 迁移包（`store/migration.ts`）

`studyDays` 加进导出清单，导入时**按日期取较大值**而不是相加：相加会把同一天的时长算两遍，
直接跳过又会丢掉「另一台设备学得更久」的那一半。它不属于任何视频，因此不走
「跟随新视频写入」那条子表路径，单独一步处理。

## 5. 已知未做 / 取舍

1. **按课程维度拆分**没做（哪门课学了多久）。要做得给 `studyDays` 再加一个维度的表，
   或按视频各记一行 —— 收益是可解释性，成本是行数 × 课程数。当前只记总量。
2. **后台播放不计时**。手机上把视频切到后台听声音，人其实在学习，但 `visibilityState`
   已经是 hidden，一律不计。放宽这条需要引入「媒体播放中就算在线」，与「切走就不算」的
   直觉冲突，暂不做。
3. **多标签页同时开会重复计时**（两个标签页各算一份）。这是刻意不做的：要修就得引入
   跨页心跳（BroadcastChannel / Web Locks），复杂度远超收益，且「同时开两个标签页学习」
   本身就是罕见姿势。
4. **空闲阈值不随媒体时长自适应**（比如播客类的长音频）。目前播放中一律豁免，
   暂停后按阈值判。
5. **已修的口径错位（记录在此，别再犯）**：「近 7 天」这张卡一度把全期的
   `averageSeconds`（`totalSeconds / activeDays`）当成自己的日均显示。截图复核时发现：
   卡片标题说 7 天，副文案却是 15600s ÷ 4 天 = 65 分，而窗口内其实是 140 分 ÷ 3 天 = 47 分 ——
   数字本身没错，错在它被挂到了另一套口径的标题下。
   修法是给 `computeStats` 补一个窗口口径的 `weekActiveDays`，把全期日均挪到「累计学习」卡，
   「近 7 天」改报窗口内活跃天数；单测与 e2e 各加一条断言钉住（单测造「很久以前学过很多、
   近 7 天只学 10 分钟」的数据让两个口径差一个数量级，混用必然被测出来）。
   教训：**统计量要跟它的分母一起看**。`averageSeconds` 这种自带隐含分母的字段，
   名字里没写「全期」，靠自觉是守不住的，得靠注释 + 断言。
