# 评论区（AI 生成的同学讨论）设计

- 状态：**已实现并回归**（`test-comments` 24/24、`e2e-comments` 19/19，截图见 `e2e-shots/comments/`）
- 日期：2026-09-22
- 需求：播放页视频下方加一块 YouTube 式评论区，**点开就有内容**（不是空着输入框等人写）

## 1. 背景与目标

播放页现在有五个面板（字幕 / 讲义 / 问答 / 弹幕 / 卡片），其中「弹幕」与「问答」已经占了「对课程内容说话」这两格：

| | 弹幕 | 问答 | 评论区（本次） |
|---|---|---|---|
| 谁在说 | AI 代你说 | 你问、AI 答 | 多人并列（AI 角色） |
| 说什么 | 单句思考题 | 长回答 + 检索 | 围绕某一时间点的多轮讨论 |
| 怎么用 | 飘过即忘 | 一对一深挖 | 可排序、可回复 |

**要补的是第三格**：弹幕是一句话飘过、无回复，问答是一对一 —— 缺的是「多人围绕同一个时间点的讨论」这种形态。看课时最想知道的是「这块别人怎么看、哪儿容易栽」，这类信息天然是**讨论**而不是单向问答。

目标：视频下方一块评论区，按课程内容生成若干讨论串，每条锚定一个时间点，时间戳可点跳转，二级回复，可按热度 / 进度排序。

**非目标（明确不做）**：

1. **不做用户发帖**。本次内容全部由 AI 生成，评论区是只读的。想加本地笔记是另一个功能（届时「讨论」会变成双向，需要重排 UI 与数据模型）。
2. **不做点赞 / 点踩**。单机没有社交回路，编出来的数字会让人怀疑整块内容的真实性 —— 排序改用「回复数」这个真实存在的量（见 §3.3）。
3. **不拉 B 站真实评论**。`x/v2/reply/wbi/main` 要 wbi 签名且有风控，二级回复还要翻页，工程量和风险都明显高于本方案，值得单开一份设计。
4. **不覆盖阅读材料**。评论锚定的是「秒」，材料只有页 / 段。材料页继续只留问答（`MATERIAL_PANEL_KEYS` 不动）。

## 2. 不变量

1. **播放页不做整页滚动。** `.player-layout` 是 `overflow: hidden` 的固定高度布局，整页滚动会让视频在手机上一滑就没了。评论区必须是**带自身滚动的区块**，高度有上限。
2. **默认折叠。** 视频的 16:9 尺寸由宽度反推、在 pane 里居中，这是 YouTube 式 UI 改造定下的观感。默认展开会把窄屏下的视频压到不可用 —— 而用户 90% 的时间在看视频。折叠态只留一行 affordance。
3. **时间戳跳转沿用既有约定**：点一条 → `playerRef.current.currentTime = t + 0.01`（与字幕 / 弹幕 / 卡片完全一致）。
4. **面板的 `data-testid` 契约不变**：`panel-tab-*` / `panel-slot-*` / `[role="tabpanel"]` / `.sub-item`。评论区是**区块不是面板**，不进 `mdui-tabs`，也就不动 e2e 那批选择器。
5. **时间戳必须钳制。** 模型很容易编出视频里根本没有的时间点，点了跳过去是黑屏或结尾 —— 与弹幕同款钳制（落在本块范围内 ±60s 才收）。
6. **不新增第二套网络层**：复用 `api/siliconflow` 的 `chatOnce` 与 `utils/concurrency` 的重试 / 并发池。

## 3. 设计

### 3.1 形态

`.video-pane` 内、播放器下方：

```
┌─ video-pane ────────────────────────┐
│         [  播放器 16:9  ]           │  ← 折叠时与今天完全一致
│  ┌───────────────────────────────┐  │
│  │ 讨论区  12 条    ⌄           │  │  ← 折叠条（约 44px）
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

展开后折叠条下方长出内容区：工具条（生成 / 重新生成 · 排序 · 模型）+ 讨论串列表，**自身滚动**，`max-height` 取 `min(34vh, 320px)`（≤900px 收成 `min(30vh, 280px)`，手机与矮屏横屏再收到 `min(26vh, 220px)`）。

- 折叠条上直接给**条数**：`讨论区 · 12 条讨论 · 20 条发言`。0 条时文案换成「还没有讨论」/「需先生成字幕」，与弹幕面板的空态同款。
- reason：折叠态是唯一能同时满足不变量 1 与 2 的形态。代价是「最像 YouTube」的那点观感打了折 —— YouTube 评论区是直接铺开的。**实测后的结论**：宽屏下也确实用不着默认展开，播放页的第一眼应该给视频（`e2e-shots/comments/` 里有 1280×800 / 1280×900 / 1600×1000 三档的实测几何）。

### 3.2 数据模型

`db.ts` 加表，`version(12)`：

```ts
export interface CommentRow {
  id?: number;
  videoId: string;
  /** 时间锚点（秒） */
  time: number;
  /** 角色名，取自固定名单（见 §3.4），让整门课里同一个人前后一致 */
  author: string;
  /** 发言类型，决定标签样式与排序权重 */
  role: 'ask' | 'answer' | 'note';
  text: string;
  /** 二级回复：指向同一视频内父评论的 id。**非索引字段** */
  parentId?: number;
  createdAt: number;
}
```

索引 `++id, videoId, time`（与 `danmakus` 同构）。`parentId` 不做索引：取一节课的评论本来就是 `where('videoId').equals(id).toArray()` 一次全取，分组在内存里做 —— 与 `SegmentRow.cues` / `ChatRow.images` 沿用同一条先例，**不需要为它单独升版本**。

**只做两层**（父 → 回复），不做无限嵌套：YouTube 也只有两层（回复的回复都摊平在同一层）。三层以上在窄屏里缩进会吃掉一半宽度。

### 3.3 排序

两档，默认「热门」：

| 档 | 规则 | 为什么 |
|---|---|---|
| **热门** | 回复数降序 → 时间升序 | 没有点赞数可用（非目标 2）。回复数是在这套数据里唯一真实的「热度」信号：讨论越热，回复越多 |
| **按进度** | `time` 升序 | 跟着课程进度一路看下去，是学习工具里最自然的读法 |

**刻意不做 YouTube 的「最新」**：内容是 AI 一次性生成的，`createdAt` 只差几秒，「最新」等于随机顺序，给它一个 tab 只会让人以为坏了。

### 3.4 生成流水线

`src/pipelines/comments.ts`，骨架与 `pipelines/danmaku.ts` 同构（切块 600s → 单块失败不阻断 → 整片重生成），差异有三处：

- **并发与重试用 `utils/concurrency` 的 AIMD 原语**（`AdaptiveLimit` + `adaptivePool` + `withAdaptiveRetry`），不再像弹幕/卡片那样各带一份 `withRetry` + `pool`。那两份是纯函数拷贝，本次**刻意不动它们**（已各自回归过，为一个 15 行助手动它们的收益不抵风险）—— 收敛的落点建议 `pipelines/jobKit.ts`，注释里写了。
- **每个字幕块产出至多 2 条主贴 + 每条 1~3 条回复**。取 2 是为了对齐「约每 5 分钟 1 条」的密度：2 小时的课约 24 串、50 条发言，与真实视频的评论区量级相当。这是上限不是指标，提示词同时要求「没有值得讨论的内容就返回空数组」。
- **角色名必须从给定名单原样复制**：`小林 / 阿哲 / Lily / 老王 / 助教`。不限定的话模型每块都会发明新名字，整片看起来像换了一班人（`routeSkills` 的「从列表原样复制」是同一手法）。`COMMENT_AUTHOR_POOL` 是提示词与清洗层**共用的同一份来源**，`test-comments` 里有契约断言守着它。

主贴偏向 **易错点 / 常见误解 / 为什么**，回复承担「解释 / 补充 / 反问」。这条是**与弹幕的错位设计**：弹幕负责「启发式追问」，评论区负责「围绕它的讨论」。不写死的话两边会生成同一批问题，用户会看到重复。

落库前先删该视频的旧评论（`where('videoId').equals(id).delete()`），与弹幕一致。写入是**两阶段**（先主贴拿自增 id、再写回复）—— 评论总量只有几十行，顺序 `add` 的代价可以忽略，但「父 id 一定拿得到」是硬保证。

### 3.5 纯逻辑分离（能不能被测的关键）

模型输出解析必须能在 Node 里单测，所以逻辑全放在**零依赖模块** `src/harness/comments.ts` —— 与 `ankiCard.ts` / `quiz.ts` 同构（那两个也是「LLM 输出清洗 + 零依赖可单测」），放一起才好找。它连 `store/db.ts` 都不 import：`groupThreads` 的入参只要结构化匹配（`CommentRowLike`），所以单测进程不会被 Dexie 拖进来。

- `parseCommentThreads(text, range)`：剥离围栏 → 取 JSON → 逐字段校验 → 角色归一 → 文本清洗与截断 → 时间戳钳制 → 条数上限。
- `cleanText` / `normalizeAuthor` / `normalizeRole`：三条归一规则各自独立可测。
- `orderThreads(threads, sort)`：两档排序的纯函数实现（不改入参）。
- `dedupeThreads(threads)`：跨块聚合时的重复剔除（弹幕用的是「最小时间间隔」，评论用**主贴文本前 12 字相同**判定 —— 时间上可以紧邻，但同一个问题不该问两遍）。
- `groupThreads(rows)` / `countComments(rows)`：两层结构还原与计数，展示层直接用。

组件与流水线只做「取数 → 调用 → 落库 / 渲染」，不藏业务判断。

### 3.6 正文不做 Markdown

评论正文**纯文本渲染**，时间锚点只由行首的时间 chip 承担（点击跳转）。虽然 `linkifyTimestamps` 现成可用，但接 Markdown 渲染要给评论区拉进一整套渲染依赖，而正文里那几个 `[12:34]` 完全可以让模型别写 —— 提示词里直接禁止在正文里写时间戳。清洗层还顺手把 `[12:34]` 变成裸的 `12:34`：留着方括号会让人以为能点（点了没反应）。

### 3.7 与「弹幕」的边界要在提示词里写死

两者的输入都是字幕 —— 不写死就一定会出同一批问题，用户会看到「弹幕问了一遍、评论区又问一遍」。于是：弹幕写「启发式追问」，评论写「围绕一个易错点的多轮讨论」，并且明确**禁止复述老师原话、禁止写成知识点总结**。
