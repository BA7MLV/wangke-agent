## 1. 2026 年的 SOTA 是什么

先把「标准答案」说清楚，再谈哪些能在本项目落地（§2）。

### 1.1 共识管线

各方来源（Anthropic 的 contextual retrieval 研究、各家 2026 生产实践总结）指向同一条管线：

```
（多轮）查询改写
  → 混合召回：dense top-50  ∥  词法 top-50
  → RRF 融合
  → cross-encoder 重排序（50 → 5~8）
  → 上下文装配（去重、按「最强的最前与最后」排序、带引用）
  → 生成（只依据给定上下文，找不到就说没有）
```

### 1.2 各阶段的公开增益

数字来自厂商研究与生产团队博客，**方向可信、具体数值不可当常量**（样本与语料都不同，多数未经第三方复现）：

| 阶段 | 报告增益 | 来源 |
|---|---|---|
| Contextual retrieval（入库时给每块补一句上下文再 embed） | 检索失败率 5.7% → 2.9%（−49%） | Anthropic |
| 再叠加重排序 | 5.7% → 1.9%（−67%） | Anthropic |
| 混合检索（dense + BM25 + RRF） | MRR 约 57% → 66% | 单一 benchmark，未复现 |
| Cross-encoder 重排序 | precision +15~30%；context precision 0.61 → 0.71（混合）→ 0.79（+重排） | Cohere / 单一已发表管线 |
| bge-reranker-v2-m3（开源自杀） | +12~25%，单对约 15ms（GPU） | 同上 |
| MS MARCO recall@10 | 混合 80.8% vs dense 13.9% vs BM25 11.9% | 单一数据集，**量级可疑，仅作方向参考** |

### 1.3 与「长上下文取代 RAG」的关系

结论是**互补，不是替代**，三条硬理由：

1. **成本**：注意力是二次的。整个语料塞进 prompt 比只取需要的块贵几个数量级。
2. **延迟**：TTFT 随 prefill 线性涨；几十万 token 的首字节要数十秒，在 agent 循环里是致命的。
3. **质量**：**lost in the middle** 是结构性的 —— 相关信息落在中段时性能降 >30%；Anthropic 2026 的长上下文评测里，1M token 的 needle recall 只有 10k token 的约 60~70%。窗口变大解决不了，反而把相关内容推得更靠中间。
4. LaRA benchmark：精心选的 48K token RAG 比 117K token 全文塞入高 **13 个 F1**，token 只用约 1/7。

长上下文真正改变的是**每步的工作集可以更大**：从「取 5 块」变成「取 20~40 块再交给模型推理」。也就是 §1.4。

### 1.4 分层与目录（与「课程变多」直接相关）

- **RAPTOR**（递归聚类摘要树）在「通读整篇才能回答」的问题上增益很大（QuALITY 62.3% → 82.6%），但有一个明确的代价叫 **staleness**：摘要树是预计算的，改一篇文档会逐层作废上面的摘要。原论文默认语料不动 —— 后续专门有论文给动态语料打补丁。
- **GraphRAG**：多跳与实体关系问题最强，但索引成本最高（全语料 LLM 抽实体），且**在简单事实问题上常不如朴素 RAG**。
- **分层索引（目录式）**：文档摘要 → 章节 → 细粒度块，检索由粗到细。「索引成本中等、复杂度低」，但**层级必须真的贴合内容结构**，层级建错比平铺检索更差。

对本项目：**不做 RAPTOR 全局树、不做 GraphRAG，做「每门课各自的层级 + 课程目录层」**。理由在 §3.3：新增一门课只该影响这门课，不该作废全局结构。

### 1.5 RAG 还有存在的必要吗

这个问题必须分三层回答，混在一起谈就会得出错误结论。

**第一层：那套「架构」——不需要存在了，而且正在被拆。**

chunk + embed + 向量库 + top-k 作为**默认架构**的范式，2026 年的定论已经很明确。即便支持 RAG 的一方也承认：独立向量库作为默认架构组件「承受压力」，向量检索「越来越成为既有数据平台里的一个能力，而不是单独立一个库的理由」。拆它的理由是运维性的，而且全部真实：索引漂移、chunking 反复返工、embed→retrieve→rerank→synthesize 的延迟叠加、以及「量了一堆检索指标却仍然给出用户不信的答案」。
**本项目的 §3.1 就是一个索引漂移事故** —— 这不是巧合，是这类架构的固有失败模式。

**第二层：「检索」这件事——无条件需要，而且证据比一年前更硬。**

| 证据 | 结论 |
|---|---|
| Chroma《Context Rot》（2025-07），测 18 个前沿模型 | 准确率随上下文长度增长而下降，**与模型无关** |
| Databricks 长上下文 RAG 评测 | 正确率在**约 32,000 token** 处开始下降 |
| LaRA benchmark | 48k token 的 RAG 比 117k token 全文塞入高 **13 个 F1**，token 只用约 1/7 |
| 成本测算（10k 查询/日，Sonnet 级） | 检索比长上下文便宜 **7~12 倍**（$900/日 vs $6,300/日） |
| 场景覆盖 | 「检索加持的长上下文」在 8 类企业场景里**赢 7 类** |

关键是：**这些结论都与「语料塞不塞得下」无关。** `context rot` 不在意你塞得下 —— 塞得下也照样退化。这是「既然窗口够大就全塞进去」这个论证一直漏掉的部分。

**第三层：「embedding」这个具体原语——需要，但只为某一类查询，且必须由评测证明。**

见 §1.1 的那张图：不知道术语的概念型提问（「这段没听懂」）是词法**零命中**的场景，也是 embedding 唯一不可替代的场景。而它占你实际提问的多大比例，**不该靠先验判断，该靠 §4.8 的评测集测出来**。

**落到本项目：32k 这个数字直接命中你。**

一门 2 小时课的字幕是 **3~4.5 万 token** —— 正好压在 Databricks 测到的掉点区上。所以「把整门课塞进上下文」看起来是免费午餐，实际上**恰好落在退化区**，不是稳赢。
而另外两类语料**定义上就超窗**：一份教材 PDF 30 万 token 起，课程库 30 门 100 万 token 起（后者正是库级问答要面对的）。

**一个必须承认的让步**：如果今天从零设计，我不会从 embeddings 开始。顺序会是「结构层（§4.2，讲义大纲现成）→ 词法（§4.3）→ 评测（§4.8）」，先用评测证明前两者够不够，再决定 embeddings 是否需要介入。
**不建议现在拆掉 embeddings 的唯一理由是沉没成本**：它已经建好了、钱已经花了，拆掉是纯亏损，而降级成「三个原语之一」是零成本。

### 1.6 embeddings 的存废判据

上面第三层留了个「必须由评测证明」的尾巴。这里把它写成**可证伪的判据**，而不是继续用论证解决。

**先纠一个因果：2023 年 RAG 需要 embeddings，是因为「检索器要给一个只能看 4k token、且只看一眼的模型做预筛」。** 词汇鸿沟（问句用词 ≠ 原文用词）必须由检索器在检索时解决，因为模型帮不上忙。

**本项目里这个前提不成立**：消费检索结果的是工具循环里的一个强 LLM。词汇鸿沟因此从检索器搬到了 LLM 身上 —— 而在那里它很便宜就能解决（生成同义词、从划选的原文里直接取词、读章节标题导航、迭代）。这正是 Claude Code 那条结论的核心，**它对本项目成立不是因为语料像代码，而是因为循环已经存在**。

三类查询各自的判断：

| 查询类型 | embeddings 的作用 |
|---|---|
| 编号 / 专名（「第 4 条规则」） | 无用。词法完胜 |
| 全局（「哪门课讲过 X」） | 无用。结构层完胜，两者都不需要 |
| 概念型（「这段没听懂」） | **被认为不可替代，但本项目已有划词 / 框选**：agent 手上有选中的原文，可以直接用原文里的词去检索，不需要跨词汇鸿沟。纯文本提问时 agent 可以自己生成候选词再检索 —— 代价是 1~2 轮，不是一堵墙 |

**一个反直觉但成立的论据（支持词法）**：embedding 模型对**低频自造术语**的表征不稳定 —— 训练语料里没见过的词，在向量空间里位置飘忽，很容易召回「语义相邻但完全不对」的内容；而词法会直接锁定那几个字。**课程里恰恰充满这种词**：老师自造的讲法、讲义里的专名、缩写。也就是说，在你最在意的那些术语上，稠密向量的可靠性反而更低。

**必须承认的弱点（支持 embeddings）**：中文没有词边界，而 BM25 本身不做分词 —— 中文 BM25 的质量取决于分词质量。字符 bigram 是绕过分词器的常用做法，但不如好的分词。这是 embeddings 在本项目里最站得住脚的立足点，不要低估。

**判据（可测，不需要 API key）**：

1. 先只做词法（§4.3），跑 §4.8 的离线评测档。
2. 统计两个数：**空手而归率**（该问题在语料里确实有答案，但召回为零）与 **recall@5**。
3. 按查询类型分开看 —— 关键是第三类。
   - 第三类空手率低 → **embeddings 可以删**，省下索引、指纹、重建逻辑与「无 key 不可用」这个产品缺陷。
   - 第三类空手率高 → 保留，但要**把依赖方向倒过来**：改成「词法为主、embeddings 为增强」，而不是现在的「无 key 即无检索」。

第 3 条的措辞是重点：**无论结论如何，把依赖方向倒过来都是净收益**。它和精度无关，是产品层的改善 —— 没有 API key 的用户现在完全不能用检索，改完之后是「弱一点但能用」。

## 2. 本项目栈的约束 → 哪些能做

| 标准做法 | 本项目能不能做 | 替代方案 |
|---|---|---|
| 向量数据库 / ANN 索引 | 不能（IndexedDB + Dexie） | 分批全扫 + 只留 topK（见 library-chat 设计 §3.3） |
| BM25 倒排索引库（ES / rank_bm25） | 不能（无依赖、无服务） | **内存词法打分**：语料总量很小，全扫即可（§3.4 给出量级论证） |
| Cross-encoder 重排序（本地 ONNX） | 技术可行（已有 `onnxruntime-web`）但模型体积 100MB+，首次下载不可接受 | **硅基流动 `/v1/rerank`**：同一个 API Key，`BAAI/bge-reranker-v2-m3` / `Qwen3-Reranker`（§3.5） |
| Prompt caching 摊薄长前缀成本 | 不可依赖（取决于 provider，无标准保证） | 不把「上下文尽量短」当成省钱手段，而是当成质量手段 |
| Contextual retrieval（每块一次 LLM 调用） | 成本过高（一门 2 小时课 ≈ 数百块 ≈ 数百次调用） | **零成本版**：用已有的讲义大纲做结构前缀（§3.7） |
| RAPTOR 全局摘要树 | 不建议（staleness + 重建成本） | 每门课自己的画像 + 章级摘要（§3.3） |
| GraphRAG | 不做（实体抽取成本 ≫ 收益） | 明确列入非目标 |

## 3. 现状差距（逐条，带位置）

按严重程度排序。第 1 条是**正在静默损坏数据**的 bug，不是优化项。

### 3.1 换 embedding 模型后，材料索引永久失效（bug，**P0 已修**）

`Settings.tsx:401` 在确认更换模型后执行 `db.embeddings.clear()` —— **只清了视频字幕向量，没有清 `db.materialEmbeddings`**。

而两条索引链路都是「已有向量就跳过」：`embedIndex.ts:55`、`embedMaterial.ts:54` 都用 `doneIds` 过滤。`ChatPanel.tsx:411` 又只在 `embCount === 0` 时才触发重建。

所以后果是：换模型后，视频向量被清空并按新模型重建，材料向量仍是**旧模型**的；查询向量来自新模型，与旧向量算余弦 —— 材料检索**永久退化为跨向量空间的垃圾相似度，且没有任何提示、永远不会自愈**。

**修法**（见 §8 的实现记录）：加指纹（§4.1）让这件事从根上不可能发生 —— 过期行被判为待建，索引计数只认指纹一致的行，于是「过期」如实表现为「未就绪」。`Settings.tsx` 同时改成清两张表，作为一道显式的、可读的保险。

### 3.2 向量不带任何指纹

`embedIndex.ts:71` / `embedMaterial.ts:70` 存的是 `{videoId, segmentId, vector}`。没有 `embedModel`、没有维度、没有分块版本。

后果：无法检测混用、无法局部重建、无法自愈。§3.1 的 bug 之所以能存在，根因就是这里。

### 3.3 单路召回，没有词法通道

`search.ts:27` 的 `searchTranscript` 只有 dense cosine，`topK = 6`。对专有名词、缩写、公式编号、规则条号这类**字面精确匹配**的查询天然失效 —— 而这恰恰是网课场景的高频问法（「那个 XXX 定理」「第 4 条规则怎么说」）。检索失败的根本原因在这里，换更强的模型救不回来。

### 3.4 没有重排序

`search.ts:42` 是 `hits.sort().slice(0, topK)`。dense 的前 6 名是「向量空间里最相似」而不是「最相关」。所有来源都把重排序列为 ROI 最高的一步，本项目一步都没做。

### 3.5 没有课程目录层

库级问答若直接全库扫描向量，课程一多，延迟与信噪比同时退化。

### 3.6 分块无重叠

`chunk.ts:149` 的 `splitLongText` 按句边界切、`MAX_BLOCK_CHARS = 800`，**切点没有重叠**。答案跨切点时两半各丢一半 —— 这就是各来源反复提到的 context-cliff。

### 3.7 上下文装配过于朴素

`context.ts:9` 的 `fitHistoryToBudget` 只按 token 预算从新到旧取历史；检索结果按分数顺序直接拼。没有去重、没有「最强的最前与最后」、没有相邻扩展、没有按来源分配预算。

### 3.8 没有检索质量评估

没有任何 golden set，也就没有任何「这次改动到底涨了还是掉了」的证据。这是「必须保持最优质上下文」这句话无法被验证的原因。

## 4. 设计

### 4.1 索引指纹与自愈（地基，**已实现**）

落点 `src/harness/indexFp.ts`，零依赖、可 Node 单测（与 `skills/scope.ts` 同一条先例）。指纹：

```ts
embedFingerprint(embedModel)  // => `v1:Qwen/Qwen3-VL-Embedding-8B:c1:x1`
                              //     ↑格式版本  ↑模型            ↑分块  ↑上下文增强
```

两个版本号是**手动**常量（`CHUNK_VERSION` / `CONTEXT_VERSION`），不是从参数自动生成 —— 参数会改回原值，自动生成的指纹会把「改了又改回来」判成没变，而这恰恰是要防的情况。

核心是纯函数 `partitionVectorRows(rows, keyOf, validKeys, fp)`，它回答「哪些行该淘汰、哪些可复用」，被两条链路共用（`segmentId` / `blockId` 通过回调传入，不写死字段名）。

两处关键决策，与最初设想不同：

1. **过期行直接删除，而不是原地改写覆盖。** 删除期间索引处于「新向量 + 缺失」状态，最坏结果是**召回不全**（可察觉、可恢复）；而「沿用旧行、边用边重建」会让两个向量空间共存，产生**静默的错误相似度**（不可察觉）。宁可少，不可错。
2. **索引计数也必须是「只数指纹一致的行」。** 只改建索引函数不够 —— `ChatPanel` 是先比计数、再决定要不要调建索引。按行数比会得到「已就绪」，重建永远不会被触发（这正是原 bug 的形态）。所以新增 `embeddingIndexCount()`，并把已有的 `materialIndexCount()` 改成同义：只统计指纹一致的行。这样「过期」就如实表现为「未就绪」。

**这一条是「新增课程后质量不下降」的真正答案**：新增课程、换模型、调分块，都只会让**受影响的那些行**失效并局部重建，永远不会出现两个向量空间混在一张表里。

### 4.2 课程目录层（可扩展性的关键）

新表 `courseProfiles`，一门课一行：

```ts
interface CourseProfileRow {
  courseId: string;
  /** 这门课讲什么（120 字内） */
  summary: string;
  /** 章节：标题 + 时间/单元范围 + 要点。**直接来自讲义 outlineJson** */
  chapters: { heading: string; start: string; end: string; points: string[] }[];
  /** 关键术语，字面匹配用（专有名词、公式名、缩写） */
  keyTerms: string[];
  /** 生成时的指纹，与 §4.1 同源 */
  fp: string;
  createdAt: number;
}
```

**数据来源几乎免费**：`handouts.outlineJson` 已经就是「标题 + 概述 + 章节（heading/start/end/points）」。有讲义的课直接搬；没有讲义的课用一次 `chunkSummary` 提示词生成。

库级检索变成**两跳**：

```
全库问题
  → 目录层（N 门课的画像，纯文本，量级是几十 KB）选出 1~3 门候选课
  → 只在候选课内做 dense + 词法检索
```

收益有三层：把 O(全库) 降成 O(候选课)；「哪门课讲过 X」「这门课要不要复习」这类问题本来就该在目录层回答；**新增课程只生成它自己的画像，不动其他课的画像** —— 这正是相对 RAPTOR 全局树的核心优势。

课程画像同时是库级问答提示词里「你有哪些课」的注入源，也是课程名 → id 反查的来源。

### 4.3 词法通道 + RRF

**为什么值得做（2026-09-23 修正）**：初版把它的价值写成「长尾精度保险」。那个定位低估了它。真正的理由有三条，**都不关于精度、也不依赖 API**：

1. **它让应用在没有 API key 时仍然可用。** 现状是 `ensureEmbeddingIndex` 直接抛错、`searchTranscript` 要调 `embed()` —— **没有 key 就完全没有检索**。词法通道是唯一不花钱、不联网的检索路径。
2. **它不会脏。** 没有索引、没有指纹、没有重建 —— 从结构上不可能出现 §3.1 那类事故。
3. **它可解释。** 能告诉用户「搜了哪个词、命中哪几段」，向量检索只能给一个相似度数字。

对上「不知道术语的概念型提问」它是零命中，那一类仍然必须靠稠密向量（§1.5 第三层）。所以两者不是替代关系。

- 中文不做分词，用**字符 bigram** 作词项（无需分词器、无词典依赖），BM25 公式打分。
- **关键论证**：不需要倒排索引。量级估算 —— 一门 2 小时课约 3 万字，30 门课约 100 万字；在 JS 里对这 100 万字做一遍扫描 + 打分是**几十毫秒量级**，而且只在候选课范围内做（§4.2 之后通常只有 1~3 门课、几万字）。为这个规模建倒排索引是过度工程。
- **必须是打分式而不是裸 substring。** 代码里 grep 精确，前提是标识符稀有；中文散文上裸 grep 一个常用词会返回几十上百段、直接冲爆上下文。这是把一种失败模式换成另一种。
- IDF 用候选集内的文档频率近似（标准 BM25 需要全库 DF；候选集内算的近似值在有偏时仍然有效，因为 IDF 只做加权）。
- **RRF 融合**（`k = 60`，原文经验值，不需要调）：`score(d) = Σ 1/(k + rank_i(d))`。只用排名不用分数，天然避开 cosine 与 BM25 分数尺度不可比的问题。
- 注意：RRF 需要两路各召回 **50** 条（不是 6 条）才有融合的余地。这与现状的 `topK = 6` 是两个不同阶段的参数。

### 4.4 重排序

`api/siliconflow.ts` 加一个端点，与现有 `embed()` 同构：

```ts
export async function rerank(s: Settings, model: string, query: string, documents: string[], topN?: number)
// POST /rerank  { model, query, documents, top_n }  →  results: [{ index, relevance_score }]
```

- 默认模型 `BAAI/bge-reranker-v2-m3`（中文稳、与现有 embed 模型同源系）。
- 管线：dense top-40 ∥ lexical top-40 → RRF → top-30 → **rerank → top-6**。
- 设置里给开关。关闭时退化为 RRF 排序，功能不缺失，只是精度低一档 —— 有些用户会不想为每轮问答多付一次调用。

### 4.5 上下文装配

- **去重**：按 `(courseId, unit)` 与文本内容 hash 双层。同一段话被 dense 与词法各召回一次是常态。
- **顺序**：最强的最前与最后（对抗 lost in the middle）。中间放次强的。
- **相邻扩展**：**复用 `context.ts:25` 的 `subtitleWindow`**，而不是新写一套 parent-child。它本来就是「从命中段向前后扩展到字数上限」，正好是 parent-child 想要的效果，且已经有测试覆盖。
- **预算按 token 分配**，不按条数 —— 条数在块长不均时会失真。
- **生成约束**：只依据给定上下文；没有就说没有；每条结论必须带引用。这三条各来源都反复强调，且**本项目已经做到了**（`qaSystem` 的规则 3 与引用规则），只需在库级提示词里按课程改写。

### 4.6 分块的两处低成本修正

- `splitLongText` 加 **10~15% 重叠**（切点前后各留一段的尾部/头部）。
- **零成本 contextual retrieval**：入库前给每块前置一行结构上下文，形如
  `《课程名》 > 第3章 分类问题 > （前文末句…）`，
  然后 embed 这个**增强文本**，但展示与引用仍用**原文**。
  这是 Anthropic contextual retrieval 的零 API 成本替代 —— 结构信息来自 §4.2 的课程画像，本来就已经生成过，不需要每块再调一次 LLM。

### 4.7 「添加课程」的两条链路

这个词有两个意思，两条都要做，但改的是不同的东西。

**（A）把课程加入对话的上下文（作用域）**
库级问答给一个课程选择器：可 pin（必选）与 drop（排除）。**直接镜像既有的技能白名单语义**（`ChatSessionRow.skillIds` 的三态）：

| 值 | 含义 |
|---|---|
| `undefined` | 不限定 —— 由目录层自己选候选课（默认） |
| `[]` | 限定，且一门课都不给 |
| `[id, ...]` | 限定为这个集合 |

判定统一走一个 `isCourseAllowed()`，**不要在调用点写 `if (ids?.length)`** —— 那会把「用户明确排除了全部课程」静默退化成「全库」。这条教训在 `store/db.ts:171` 的注释里已经写过一次。

**（B）课程库新增课程后的索引卫生**
- 新课程走**后台队列**建索引与画像，复用现有 `store/jobs.ts` / `transcribeQueue` / `coverQueue` 的模式。
- 索引未就绪的课程在 `list_courses` 里**显式标注**，让模型知道「这门课为什么搜不到」，而不是给出「课程中未提及」的错误结论 —— 与 `tools.ts:268` 对材料范围截断的处理是同一条原则。
- 全程不联网也能保证一致：指纹（§4.1）保证混用不可能发生。

### 4.8 评估：把「最优质」变成可验证

不给指标，「必须保持最优质上下文」就只是一句愿望。**golden set 可以自动生成**：

课程画像里每章都有要点与时间范围 → **每章自动出一道题**（题干由该章要点改写，正确答案必须落在该章的时间/单元范围内）→ 得到一份零人工的评测集。

| 指标 | 定义 |
|---|---|
| `recall@k` | 正确章的时间/单元范围是否出现在 top-k 命中里 |
| 引用忠实度 | 回答里的引用是否都来自实际召回结果 |
| 跳章率 | 命中落在错误章节的比例 |

脚本 `e2e-retrieval-eval.mjs`：无 key 档跑纯逻辑（词法打分 / RRF / 去重 / 排序 / 指纹失效判定），`--with-key` 档跑真实召回质量。**每次动检索层都要能看出 recall@5 是涨了还是掉了** —— 各来源都提到「不少团队悄悄改退化了检索却不自知」。

## 5. 优先级

**这个顺序在 2026-09-23 被重排过。** 初版把评测排在最后、把 embeddings 当作默认底座；按 §1.5 的证据，那是反的。

| 级别 | 内容 | 为什么在这个位置 |
|---|---|---|
| **P0 ✅** | 索引指纹 + 修 §3.1 的材料清空 bug | 已完成。不涨质量，但阻止**正在发生的静默损坏**，且是后面所有增量重建的前提 |
| **P1** | 评测集（§4.8） | **必须是第一个。** 它同时是「词法 vs 稠密 vs 混合到底谁好」这个争论在你语料上的唯一裁判，也是后面每一步「到底涨了还是掉了」的唯一证据。没有它，P2~P5 全是凭感觉 |
| **P2** | 课程目录层（§4.2） | 唯一**免费**的一层（讲义大纲现成）。它独立解决整类全局型问题（「哪门课讲过 X」），且是库级问答的前置依赖 |
| **P3** | 词法 + RRF（§4.3） | 理由不是精度（见 §1.5 对初版的修正：对散文语料它主要是长尾保险），而是**零成本、可离线、无脏索引**——尤其给没有 API key 的用户一条可用路径 |
| **P4** | 重排序（§4.4） | 对「概念型」查询的直接增益最大，但要花 API 钱且需真实 key 实测，所以排在免费的 P2/P3 之后 |
| **P5** | 上下文装配 + 零成本 contextual retrieval + 分块重叠（§4.5 / §4.6） | 低成本、累积收益，但要等 P1 的评测能看出它们的效果再动 |
| **待定** | embeddings 的去留与权重 | **由 P1 的实测决定**，不再作为默认底座（§1.5 第三层） |

**明确不做**：GraphRAG（实体抽取成本 ≫ 收益，且简单问题上可能更差）、RAPTOR 全局摘要树（staleness 与重建成本）、独立向量库 / ANN（IndexedDB 约束）。

## 7. 待确认 / 风险

> **升级副作用（必读）**：升级后所有老向量会被判过期，并**重建一次**（一次性 API 成本）。老数据的向量没有 `fp` 字段，而「没有指纹」与「指纹不符」在事后无法区分 —— 分不清「只是老数据」还是「换过模型留下的旧空间」，只能按过期处理。
>
> 代价可控：重建是**惰性 + 按课程**的（打开某门课的问答才建那门课），不是一次性全量；且对已经换过模型的用户，这次重建正好把损坏的材料索引修好。
>
> 想省掉这次成本的话，可以给 settings 加 `lastEmbedModel`：相等则只回填指纹、不重算。本次**不做** —— 多一个设置字段就多一条迁移路径，收益只是一次性调用费。若日后真的成为抱怨点再加。

1. **`/v1/rerank` 的计费与限流**未实测。若单次调用成本与一次 embed 相当，则在多轮问答里会明显抬高单次成本 —— 这也是要给开关的原因。
2. **字符 bigram BM25 在中文网课语料上的实际增益未验证**。可能不如 bigram + 单字混合；必须用 §4.8 的评测集实测，不能凭 SOTA 报告下结论。
3. **embed 模型是 `Qwen/Qwen3-VL-Embedding-8B`（VL 模型）**。若该接口支持图片输入，`frames`（讲义抽帧 + 画面描述）可以进同一向量空间，做成真正的多模态检索 —— 这是本项目一个现成但未使用的能力。需先确认接口是否接受图片、以及按图计费的量级。
4. **课程画像的生成时机与失败兜底**：导入后立即生成？还是等讲义生成完？生成失败时目录层该显示什么，需要定。
5. **`subtitleWindow` 复用于装配层**时要确认它对「非连续命中」的行为（当前是聚合多窗口并去重），以及它与 token 预算的衔接。
6. 指纹字段加在向量行上会让每行变大（一个短字符串，可忽略），但**遍历时要小心不要把它当向量读**。

起因是一个追问：「RAG 现在还有存在的必要吗」。补查后新增三条决定性证据，初版的排序站不住了。

### 存废判据补记（同日）

- 起因是追问「embeddings 真的需要做吗」。补上 §1.6，把结论从「待评测决定」落成**可证伪的判据**：只跑词法，统计第三类查询的空手率，低则删、高则保留为增强。
- 补查得到一条支持词法的反直觉论据：**embedding 对低频自造术语的表征不稳定**（训练语料没见过的词在向量空间里飘忽，易召回语义相邻但不对的内容），而词法会直接锁字。课程里充满这类词（老师的自造讲法、讲义专名、缩写）—— 也就是说在你最在意的术语上，稠密向量的可靠性反而更低。
- 同时确认了 embeddings 最站得住脚的立足点：**中文没有词边界，而 BM25 本身不做分词**，中文 BM25 的质量取决于分词质量；字符 bigram 是绕过分词器的做法，但不如好分词。这条弱点不能低估。
- **一条与精度无关的结论**：无论判据结果如何，**把依赖方向倒过来都是净收益** —— 变成「词法为主、embeddings 为增强」，而不是现在的「无 API key 即无检索」。这是产品层缺陷，不是技术债。

## 9. embeddings 已整体移除（2026-09-24）

**决定**：不做 embeddings，直接删除。这是用户拍板的，**跳过了 §1.6 的判据流程**（即「先只做词法、统计空手率、再决定去留」）。记录在此以便日后回溯：这是一个**未经实测的取舍**，不是测出来的结论。

### 实际做了什么

先顶上、再拆 —— 顺序不能反：词法没就位就删掉稠密检索，`search_transcript` 会失去唯一的召回手段，agent 只剩 `get_transcript_range`（得先知道时间点才能用）。

| 层 | 改动 |
|---|---|
| 新增 | `src/harness/lexical.ts` —— CJK 单字 + 邻接二字组分词、BM25 打分、覆盖率加成。零依赖、Node 可测 |
| 替换 | `searchTranscript` / `searchMaterial` 内部改为词法，**函数签名与返回类型不变** → tools / prompts / 调用点几乎不用动 |
| 契约 | `tools.ts` 的两个检索工具改为要求传**关键词短语**；`prompts.ts` 两条规则改为「一次不中就换一组说法重试」 —— 词法检索下这是必要行为，不写死会退化成噪声排序 |
| 拆除 | `embedIndex.ts` / `embedMaterial.ts` / `indexFp.ts` / `utils/embed()` / `settings.embedModel` / 设置页 Embedding 槽位与更换确认框 / `sync/units.ts` / `migration.ts` / 存储统计的分类项 / `Library.tsx` 级联 / `materialJob.ts` 的建索引段 / `jobs.ts` 的 `index` phase |
| Schema | `version(13)` 用 `null` 删掉 `embeddings` + `materialEmbeddings`（同时回收磁盘：一门 2 小时课约 2MB） |
| UI | `ChatPanel` 拆掉整段「查向量计数 → 建索引 → 等待索引就绪」的 effect 与 `indexReady` 门禁 |

### 收益（与精度无关的部分）

1. **没有 API Key 也能检索。** 原来是 `ensureEmbeddingIndex` 直接抛错、完全不可用。这是产品层缺陷，现在消失了。
2. **不可能再有索引过期。** P0 修的那个 bug（换模型后材料检索永久退化）整类不存在了 —— 没有索引可脏。
3. **少一层网络往返**，每次检索不再需要 embed query。

### 代价与残留风险

1. **未经实测。** §1.6 设计的判据没跑，所以「词法够不够用」是**判断**而非**数据**。
   最需要盯的是第三类查询（「这段没听懂」这类不知道术语的提问）。**目前唯一的缓解是划词/框选**：agent 手上有选中的原文，可以直接用其中的词检索 —— 那条路径下词法够用。纯文本提问时依赖模型自己换词，失败模式是「空手而归」，表现为「课程中未提及」。
2. **中文分词质量。** BM25 本身不做分词，字符单字 + 二字组是绕过分词器的做法，精度不如好的分词。这是移除 embeddings 后最实质的弱点。
3. **P0 的工作被删了。** 指纹机制（`indexFp.ts`）随表一起删除。它在升级窗口期挡住了污染，但寿命只有一天 —— 复盘时值得注意：**当一件事的上游可能被整体拿掉时，先确认上游的去留再动它的基础设施**。
4. **`test-index-fp` 已删，`test-db-schema` 补上** —— 删表是本次唯一会丢数据且改不回来的改动，必须有守卫。

### 建议的下一步（补偿，未做）

**结构层（§4.2 课程目录层）的优先级现在更高了**，因为它同时补偿了移除 embeddings 的损失：把讲义大纲（章节 + 时间范围 + 要点）暴露成一个工具，agent 就能靠目录导航回答「哪门课讲过 X」这类全局问题，而不依赖任何检索原语。这是当前最高性价比的下一步。
