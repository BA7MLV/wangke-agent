# 数据加载的骨架屏方案（延迟门控）设计

日期：2026-10-15
状态：**已落地**（`ui/skeleton.tsx` + `ui/skeleton.css`，接入 `pages/Library.tsx` / `pages/CourseChat.tsx` / `pages/Study.tsx`；量测与断言在 `scripts/probe-loading-latency.mjs`）

## 背景与目标

「数据加载要不要上骨架屏」这件事，第一反应通常是「要，业界都在用」。但**用了什么**和**有没有用对**是两件事，而本项目恰好是一个用错会立刻变成负收益的场景。

先说事实（全部来自 `scripts/probe-loading-latency.mjs`，原始数据 `scripts/.cache/loading-latency.json`）：

| 量测项 | 结果 |
| --- | --- |
| IndexedDB 直读 `videos` 全表（冷连接） | p50 **0.3ms** |
| IndexedDB 直读 `videos` 全表（复用连接，即 app 里的常态） | p50 **0.1ms** |
| 资料库有数据冷启动 → `video-item` 首现 | 377 / 689 / 1051ms（三轮） |
| 同一场景**最长长任务** | 125 / 174 / 425ms |
| 同一场景 `empty-state` 的可见窗口 | **64 / 65 / 94ms** |

把这些数字放在一起，结论是反直觉的：

1. **这里根本没有可等的 IO。** 读回是亚毫秒级，而首屏要 400–1000ms。时间花在**主线程**（整包 JS 的解析执行 + 首帧渲染）上，不在存储上 —— 存储与长任务差三个数量级。
2. 那 64–94ms 的「空态一闪」**不是等待**，是**判据错了**（见 §一）。
3. 对亚毫秒级的等待插一屏骨架，只是把「闪一下空态」换成「闪一下骨架」。**负收益。**

所以本轮的目标不是「加上骨架屏」，而是：**把骨架屏放到它真正该出现的那条路径上，并且让它在不该出现时一次都不出现。**

## 不变量

写错就会坏掉的硬约束，后面每一条取舍都是在守它们：

| 编号 | 不变量 | 破坏它的后果 |
| --- | --- | --- |
| **I1** | 空态只在 `loading === false && 确实为空` 时出现 | 「未加载」被当成「确实为空」——就是 §一 那个 bug |
| **I2** | 加载在 `delayMs`（200ms）内结束 → **骨架一次都不出现** | 把一次不可感知的等待变成一次可见的闪烁 |
| **I3** | 骨架一旦露出就至少待 `minVisibleMs`（400ms） | 「骨架闪一下被内容顶掉」比不显示更让人烦躁 |
| **I4** | 骨架的几何与真内容**对齐**（复用真内容的包裹类，由 H 组按 ±4px 断言） | 加载完再抖一下，比不显示更差 |
| **I5** | 任何显式的加载态都必须有**结束条件** | 永久骨架 / 永久空白（§三 末的 `coursesStuck` 就是这条的产物） |
| **I6** | 加载态**不许把错的数字写进界面** | 「0 分钟 / 连续 0 天」——不是在等，是在报一个错的数 |
| **I7** | 刷新（非首次加载）不得回退到 `loading`，也不得把已有内容换成骨架 | 每次后台悄悄重读都配一屏骨架 |
| **I8** | 骨架不冒用真内容的 `data-testid` | e2e 在骨架阶段就误判「列表出来了」 |
| **I9** | 骨架的填充色必须**在细条上也读得出来**（大块撑得住的淡色，细条上会消失） | 「有盒子、没东西」——几何全对，肉眼一片灰（§五） |

## 一、真正的 bug：把「未加载」当成「确实为空」

```tsx
// 改前 Library.tsx:1284
{videos.length === 0 && folders.length === 0 ? (
  <EmptyState testId="empty-state" title="还没有课程或资料" />
) : ( …列表… )}
```

`reload()` 是异步 IndexedDB 读，所以**首帧这两个数组必然是空的**。于是「还没加载出来」和「库里确实没东西」被混成了同一个状态：有数据的库冷启动时，空态先出现 64–94ms 再被列表顶掉。

对照：同一份代码库里 `store/courseChat.ts` 已经把这两件事分开了，注释里明确写着禁止用 `activeId === null` 兼表「正在加载」（分别有 `loaded` / `error`）。**资料库页漏了这条规矩。**

同样的错形还出现在另外两处：

| 位置 | 错形 | 用户看到什么 |
| --- | --- | --- |
| `Library.tsx` | `videos.length === 0 && folders.length === 0` 兼表「空库」 | 有数据的库冷启动闪一下「还没有课程或资料」 |
| `Study.tsx` | `stats.totalSeconds === 0` 兼表「没有记录」 | 有一年记录的用户先看到「0 分钟 / 连续 0 天」+「还没有学习记录」 |
| `CourseChat.tsx` | `hasCourses` 在 `courseCount == null` 时兜底为 `false` | 标题先写「有什么想聊的？」再翻成「问你的整个课程库」 |

`Study` 那处尤其不能忍：**它不是在等，它是在报一个错的数。** 统计数字的空态与加载态必须分开。

## 二、阈值从哪来：两条计时规则

业界的响应时间阶梯（Nielsen 的 0.1s / 1s 两条线，Material 的「延迟指示器」同口径）：

| 等待时长 | 该显示什么 |
| --- | --- |
| `0 – 100ms` | 用户感觉是**瞬时**的 —— 什么都不该显示 |
| `100ms – 1s` | 感觉到延迟但注意力没断 —— 显示**骨架**（先把最终布局占住） |
| `> 1s` | 需要「还在动」的持续信号 |

落到实现就是两条规则，**缺一不可**（`ui/skeleton.tsx` 的 `useSkeletonGate`）：

1. **延迟门控**：`busy` 在 `delayMs` 内结束 → 一个骨架都不出；
2. **最短停留**：骨架一旦露脸就至少待 `minVisibleMs`。

第 2 条是骨架屏最常见的翻车方式：加载 250ms、骨架显示 30ms 就被内容顶掉，那**比不显示更让人烦躁**。两条规则合起来，宁可让骨架晚 200ms 出现，也不让它闪一下就走。

阈值取 `200ms` / `400ms` 而不是 `100ms` / `300ms`：这是本地 1ms 量级之上留的余量，慢设备（iPad 首次冷启动、主线程被 400ms 长任务占住）才会真正触发；快速路径上多这 100ms 用户感知不到，但能挡掉大量「其实不慢」的闪烁。

## 三、三态：`loading` / `ready` / `error`

判据从「数组是不是空的」换成显式的加载状态：

| 状态 | 渲染什么 | 空态分支 |
| --- | --- | --- |
| `loading` | 什么都不渲染（等得久则骨架） | **不可达** |
| `ready` + 真的为空 | 空态 | ✅ |
| `ready` + 有数据 | 列表 | — |
| `error` | 错误横幅 + 重试 | — |

三条实现细节，每条都对应一个具体的坑：

- **首次加载失败才切错误页。** 后续刷新（`libraryRevision` 变化、后台任务收尾）失败时，用户手里已经有一份能看的列表，一次后台重读失败把它抽走是错的 —— 内容还在、只是可能不是最新。这种情形只留一条 toast。判据是模块内的 `initialLoadSettled` ref，不是 `loadState`（后者进依赖会让 reload 每帧换身份）。
- **`error` 之前根本没有。** 原先 `reload()` 既没有 `try/catch` 也没有错误态，IndexedDB 打不开时页面停在「什么都没有」的样子 —— 用户只会以为自己的课程丢了。加 `error` 态不是为了好看，是为了把「读不出来」和「确实没有」分开。
- **刷新不得回退到 `loading`。** `loadState` 只在首次是 `loading`，之后一直 `ready`；否则每次 revision 变化都会重新走一遍骨架门控，等于给「后台悄悄重读」配了一屏骨架。

### 三态之上的第四个坑：「永远读不出来」

把「加载中」从「空」里分出来之后，多出一个新的失败模式：**如果加载永远不结束，界面会永远停在「加载中」**。

`courseCount` 就是这种字段 —— 它只由 `bootstrap()` / `refreshCourseCount()` 写入，两者都是 `db.videos.count()`，读失败时它一直停在 `null`。按「宽限期内什么都不渲染」那一档，空态会**永久空白**：没标题、没快捷提问、连「导入课程」的入口都没有。这比原来「闪一下文案」严重得多。

所以 `CourseChat` 上挂了第二道 3 秒的长门（`coursesStuck`）：越过它就认为这次计数没指望了，按「通用助手」那一套渲染。宁可退化成「没课时的样子」（用户至少还能用、还能点去导入），也不要一屏空白或一屏永久骨架。

> 这条是**修 bug 时新造出来的 bug** 的典型样本：三态本身是对的，但它把「加载中」变成了一个可以永久停留的状态。凡是引入显式加载态的地方，都要回答一句「它靠什么结束」。

## 四、骨架必须与内容同形

这是骨架屏唯一不能让的一步。形状不对的骨架 = **加载完再抖一下**，比不显示更差。

做法是**复用真内容的包裹类**，只把「该是文字 / 按钮」的位置换成灰块：

```tsx
// Library.tsx —— 卡内三层沿用真类的包裹，间距/圆角全部继承，不手写像素
<section className="library-browse">          {/* 它的 margin-top: 28px 就是工具栏的位置 */}
  <div className="library-toolbar"> …占位… </div>
  <div className="library-filter-row"> …占位… </div>
</section>
<div className="group-header"> …占位… </div>
<div className="video-grid">
  {Array.from({ length: count }, (_, i) => (
    <div className="video-row" key={i}>
      <div className="video-row__thumb skel-breathe"><span className="skel-library__badge" /></div>
      <div className="video-row__main">
        <h3 className="video-row__name"><span className="skel-bar skel-library__name" /></h3>
        <div className="video-row__meta"><span className="skel-bar skel-library__meta" /></div>
      </div>
      <div className="video-row__tags"> …占位… </div>
      <div className="video-row__actions"> …占位… </div>
    </div>
  ))}
</div>
```

- **`.skel-breathe` 只上动画、不设背景也不设几何** —— 跟任何真类叠加都不会覆盖对方的样式。
- 骨架里那些「真内容是文字」的地方，高度按**实测值**给：课程名 23px、副信息 18px、工栏标题那一行 31px。这些数不是拍脑袋，是 `probe-loading-latency` 的 H 组按 ±4px 比出来的。

### 上一版是怎么错的（这一节是本轮返工最多的地方）

上一版也写着「同形」，但做法是**手写高度去凑**：给骨架卡片画了缩略图 + 两条灰条。看着像，量出来差得远：

| 量测 | 真内容 | 上一版骨架 | 差 |
| --- | --- | --- | --- |
| `.video-row` 高 | 308px | 259px | **−49px**（少了整条操作按钮行） |
| `.video-list` 起点 y | 370 | 226 | **−144px**（工具栏那一段整体没留占位） |

两个后果都不是「看着有点糊」那么轻：

1. **卡片矮 49px** —— 内容到位时每张卡片往下长一截。
2. **起点高 144px** —— `.library-browse`（标题 / 搜索框 / 筛选行）整段是挂在**数据**上的（`videos.length > 0 || folders.length > 0`），首屏加载中它根本不存在。骨架没给它留位置，于是数据一到，这 144px 的内容从**上面**插进来，把已经画好的骨架整个往下推。

**教训：`同形` 不能靠眼睛看截图判断。** 现在它是 H 组里的一串数字（卡片高、列表起点、缩略图高、操作行高，容差 ±4px），错一像素就红。

### 顺带一个必须写明的代价

骨架卡片数（桌面 6 张 / 窄屏 3 张）是**猜的**：加载前无从知道库里有多少条。库里有 20 条时它不够长，只有 1 条时它会在内容到位后收掉一截。这是这类骨架的固有代价，取舍是「填满首屏」胜过「猜得更准」；要消掉它只能持久化上次的条数，不在本轮范围（见 §八）。

## 五、交叉淡入容器：为什么不用绝对定位

沿用仓库里既有的 `transitions.css` 第 14 节是不够的：`.t-skel` 把两层都设成 `position: absolute; inset: 0`，**两层都不参与布局，容器高度会塌成 0**。它是配着固定高度的容器用的（`HandoutPanel` 的 `.hp-legacy__skel`），列表这种高度不定的场景套不上。

`SkeletonReveal` 改用 CSS Grid 叠同一格：

```css
.skel-reveal { display: grid; }
.skel-reveal > * { grid-area: 1 / 1; }
```

两层都在文档流里，容器高度 = 较高者，不塌陷、不需要调用方报高度。只在**交叉淡入的那 400ms** 里把骨架改成绝对定位并 `overflow: hidden` —— 这样容器高度立刻等于真内容高度，「骨架比内容高」不会把页面顶起来再落回去。

另外两处取舍：

- **骨架晚一拍卸载。** `show` 翻 false 后骨架还留 `REVEAL_MS`，与内容淡入重叠。
- **但不能「`show` 为真就挂、为假就卸」。** 那样每条边界上都有一帧**两层都不在**：`show` 翻真的那一刻 effect 还没跑（骨架没挂上、内容又是空的），「晚一拍卸载」的那一拍同理 —— 400ms 的交叉淡入里插一帧空白，恰好把「不闪」这件事从头破坏掉。所以实现改成显式三段状态机 `idle → loading → revealing → idle`，**台上始终至少有一层**。
- **而且方向判断必须留在渲染阶段，不能放 `useEffect`。** 这是同一个坑的第二次踩：改成三段之后把「进 / 出」判断写进了 effect，结果那一帧空档原样回来了，只是换了位置 —— `show` 翻真的那次渲染里 `phase` 还是上一轮的 `idle`，骨架没挂、`children` 又是 `null`。修法是在渲染中直接 `setPhase`（React 会丢弃这次输出并立刻重渲染，半成品不提交，所以那一帧根本不存在），effect 只留「淡出走完 → 收干净」这段纯计时。**光看代码是看不出来的：effect 版本的类型、lint、逻辑都对，只有一帧长的空档。**
- **刻意不加 blur。** `transitions.css` 的 `.t-skel` 给一块 docx 预览加 blur 很便宜；这里是整个课程卡片列表，全列表重新栅格化在 iPad 上会掉帧。透明度交叉已经足够把「换了一层」讲清楚。

> ⚠️ 样式表的坑：`.skel-bar { height: 12px }` 是 0,1,0 特异性。业务侧只写单类（`.course-chat__empty-skel__pill { height: 40px }`）会跟它**打平**，谁赢取决于两个样式表的打包顺序 —— 表现成「药丸有时候 40px、有时候 12px」这种只在某些构建下复现的鬼影。所有业务侧的骨架几何都带父级前缀（≥0,2,0）。

### 底色：`--default-soft` 在细条上立不住

骨架的填充色一开始用的是 `--default-soft`。它是个语义令牌、深浅色自适配，看着是个稳妥选择 —— 但它等于 `color-mix(in oklab, oklch(94% .001 286.375) 50%, transparent)`，**再乘一半透明度**，落在接近纯白的底上只剩一层几乎看不见的雾。

缩略图那种大块还撑得住，**细条上直接立不住**：标题 23px、元信息 18px 那几条在实际截图里根本分不出来，整屏糊成一片灰。这一条是**截图才发现的** —— H 组的几何断言全部通过（盒子位置尺寸都对），DOM 里每个元素也都有背景色，只有把图放大 2 倍看才发现「有盒子、没东西」。

改成 `--background-tertiary`：不透明的三级面，浅色下约 oklch(91%)、深色下约 oklch(19%)，这个量级才对。同理，`tag-mini` 自己的底色 `oklch(94%)` 在真卡片里是靠**文字**立住的，只留一块色板同样看不见，也一并换掉。

还有一处顺带的：呼吸动画的谷底原本到 `opacity: 0.5`。那个幅度是配深色块用的；骨架本来就是低对比的浅灰，再砍掉一半不透明度，**呼吸的半个周期里它会淡到看不见** —— 「有东西在等」这个信号反而断断续续。谷底抬到 `0.72`。

### 怎么把「加载中」钉住（量测手法）

骨架**独占**的窗口只有几百毫秒。降速虽然能让窗口变长，但降速下「等元素出现 + 截一帧」的往返本身就要好几秒 —— 于是截图落在窗口之外是常态。这个坑踩了三次才看明白：

1. 截到的是完全就位的内容，文件名却叫 `skel-1-slow-desktop`（**静默**出错）；
2. 加上「截完回读状态校验」后，把降速从 30× 一路加到 120× **仍然全部失败**；
3. 才意识到问题不在窗口不够长 —— 而在**校验读数发生在截图之后**，测的根本不是那一刻。

正确做法是把状态钉住：让 IndexedDB 请求的 `success` / `error` 永不派发，库读一直悬着，`loadState` 就停在 `loading`，骨架稳定留在台上。不降速、不赛跑，截图想什么时候截就什么时候截，回读状态**必然**与截图那一刻一致。

实现是加一层 `open` 包装，在**捕获阶段**注册监听器并 `stopImmediatePropagation` —— 这样能同时挡住 Dexie 用的 `addEventListener` 与 `onsuccess` 属性两条路（这是实测确认过的，不是推测）。脚本见 `scripts/probe-skeleton-visual.mjs`，`probe-loading-latency.mjs` 的 H 组用的是同一份。

| `scripts/probe-loading-latency.mjs` | 新增 `library-skeleton` / `video-list` 观测点、B/A 组断言、G 组闸门双向断言、H 组同形几何断言 |

**减弱动态效果**（`prefers-reduced-motion: reduce`）：不呼吸、不交叉淡入，但**骨架照常显示** —— 骨架表达的是「布局已经知道、内容还没来」，属于信息而不是动效。

## 七、验证

`node scripts/probe-loading-latency.mjs`（需先起 preview）全部断言通过。改前 → 改后：

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 有数据的库冷启动 · `empty-state` | 闪 64 / 65 / 94ms | **从未出现**（三轮均 `null`） |
| 有数据的库冷启动 · 骨架 | —（实现里还没有） | **未出现**（正确：本机等待只有 1ms） |
| 空库冷启动 · `empty-state` | 出现 | 出现（未被三态吞掉） |
| CPU 30× 降速 · 骨架 | — | 4100–5300ms 出现 / 收走晚约 1000ms / 可见 **≈1s**，且**挂载序号早于内容**（实测 16 < 18） |
| CPU 30× 降速 · 期间 `empty-state` | — | 未出现（没有一边出骨架一边闪空态） |
| 骨架 vs 真内容 · 卡片高 | 259 / 308（矮 49px） | **351 / 350**（Δ 1px） |
| 骨架 vs 真内容 · 列表起点 | 226 / 370（高 144px） | **371 / 370**（Δ 1px） |

G 组的双向断言是重点：**只测「慢的时候出了骨架」不够** —— 那样一个「永远显示骨架」的实现也能过。必须同时测「快的时候一个都不出」（G1）与「慢的时候一定出、且待够最短时长」（G2），闸门才算被验证过。

H 组则把 §四 的「同形」从一句形容词变成四对数：卡片高、列表起点、缩略图高、操作行高，容差 ±4px。**两侧必须在同一次运行里量** —— 几何随视口变（1100px 宽下栅格是 2 列 3 行，卡片 350px 高；1280px 宽下是 3 列 2 行，卡片 308px 高），跨运行、跨视口比都没有意义。

### 降速倍数为什么要校准到 30×

G2 靠 CDP 的 CPU 降速把「真正喂给闸门的忙窗口」顶过 200ms。原来取 10×，是基于当时量到的 2507ms 首现 —— 看起来是过的。但同一份代码换一轮跑就掉到 343ms，断言随之失败。实测：

| 降速 | 忙窗口（`video-list` → `video-item`） | 骨架出现在内容之前？ |
| --- | --- | --- |
| 5× | 189ms | 否 —— 本来就短于闸门，不出骨架是对的 |
| 10× | 343ms | **不稳** |
| 15× | 560–654ms | 不稳（两轮里一轮没出） |
| 20× | 743–881ms | 出，但骨架与内容落在同一个采样点 |
| 25× | 1121–1194ms | 稳定早 186–335ms |
| 30× | 1380–1445ms | 稳定早 309–316ms |

> 表里「早多少 ms」一列只是**采样点看到的现象**，用它来选倍率，不用来下结论 —— 真结论由挂载序号闩给（见结论 3）。倍率选 30× 的理由是它留出了数量级余量：忙窗口约为闸门的 7 倍，且两轮都稳定复现。

三个结论：

1. **10× 的 343ms 是假象。** 它只比 200ms 闸门高 143ms，而且这 343ms 里还含最后一次 commit —— 真正喂给闸门的不到 250ms。断言卡在阈值边缘，就必然随机器负载翻来覆去。**任何断言都不能取「刚好越过阈值」的工况**，要留出数量级的余量。
2. **`MutationObserver` 的时间戳会被长任务「钳制」。** 回调是微任务，主线程被占住时会被推迟，回调里读的 `performance.now()` 是**推迟后**的时刻；两个节点若落在两次回调之间就会拿到**同一个时间戳**（20× 那两轮骨架与 `video-item` 都是 2884ms）。所以「A 是否早于 B」这类判断**一律不能拿时间戳相减**。
3. **DOM 快照类判据同样会翻 —— 这一条是跑全套时才抓到的。** 第二版换成了布尔闩：「某次扫描时骨架在场、内容还不在」，心想它由 DOM 状态推出、与回调何时跑无关。结果在编排器里跑全套时它挂了：骨架与内容同为 6033ms，闩读到的是「两层都在」。原因是**那次扫描本身就被推迟到了内容挂上之后** —— 只要主线程一直不松手，中间那一窗根本不会有任何扫描落点，快照类判据全部失明。

   最终用的是 **mutation 记录序号**：回调会把多次变更合并成一批，但 `records` 数组保持真实的插入顺序，且与回调何时执行无关。记下每个 testid「第一次被加进 DOM」时排在第几条，比大小即可（实测 30× 下骨架=16、内容=18）。**教训不是「换个写法」，而是「被测时刻的状态不能依赖采样」** —— 采样密度由主线程决定，而这里主线程恰恰是被测的对象。

> 顺带说明为什么 20× 的「可见 750–980ms」也不能当证据：那一段里大部分是**最短停留 + 淡出**的尾段，此时内容已经就位。可见窗口长，不等于骨架真的替内容挡过等待。

### 全套 e2e 的收口结论

`node scripts/e2e-all.mjs`（需先 `npm run build`，编排器不自己构建，且会校验「服务的产物 vs 磁盘 dist」是否同版）最终 **78 通过 / 42 失败 / 13 跳过（133，58.6%）**；本轮开始前的基线是 74 / 44 / 13（131）。两个新增脚本 `probe-loading-latency` 与 `probe-skeleton-visual` 均通过。

失败逐个对过，没有一条由本轮改动引起：

- **路由迁走导致的一大批**（`/`、`/chat`、`/settings/*` 现在都落到课程助手页）：`e2e-library` / `-copy` / `-progress`、`e2e-study`、`e2e-materials`、`e2e-course-chat-cards`、`e2e-chat-trace` 等，全是 `waitForSelector` / `setInputFiles` 超时。`e2e-chat-trace` 那条 `-28px !== 0px` 也是同一个根因：它导航到 `#/chat`，链条落在 `.course-chat__messages` 里，取到新加的 `--reasoning-sticky-gap: 28px`，而断言期望的还是没有这个变量时的 `0px`。
- **`e2e-agent-guard` 抖动**：全套负载下 `page.reload` 拿到 `net::ERR_HTTP_RESPONSE_CODE_FAILURE`，后续 evaluate 全挂在没有文档的上下文上；单独重跑即通过。
- 另有 2 条（`e2e-chat-skill-scope` / `e2e-handout-position`）从上轮的失败翻成了通过，同样与骨架无关。

修这些 e2e 属于另一件事（要么改脚本去认新路由，要么给页面补回旧路由的兼容跳转），记录在此，不在本轮顺手做。

## 八、未纳入本轮（记录，不顺手做）

1. **首屏白屏 550–620ms**（`course-chat-page` 首现 621ms、DCL 573ms）。这是当前**感知延迟最大的一项**，但它不是「数据加载」，而是整包 JS 的解析执行 —— 属于应用外壳（`index.html` 内联静态骨架 / 代码分割 / 首屏减重）的题目。混进本轮会让「骨架屏阈值」这本账算不清。
2. **模型列表**（`GET /models`，跨网络）。它是真正的网络等待，值得一套骨架，但它的加载态在 `settings/ModelsModule.tsx` 里自成一套（有 24h 本地缓存 + 过期后台重拉），阈值也该按网络量级另定，不在本机数据的口径里。
3. **`vite build` 在本机被沙箱的批量删除守卫拦住**（清 `dist/` 超过 50 个文件需确认），本轮用 `--outDir dist-skel` 绕过。与代码无关，记一笔免得下次重新查。
4. **骨架卡片数是猜的**（桌面 6 / 窄屏 3），库里条目数只有加载完才知道。想消掉这个误差只能持久化上次的条数，属于另一件事（见 §四 末）。
5. **路由迁走导致的一批 e2e 失败**（`/`、`/chat`、`/settings/*` → 课程助手页）。要么改脚本认新路由，要么补兼容跳转；与骨架屏无关，见 §七 末。
