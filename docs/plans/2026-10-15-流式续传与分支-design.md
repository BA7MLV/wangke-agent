## 背景与目标

三件事，来自同一轮需求：

1. **模型列表要缓存到本地** —— 设置页的「拉取模型列表」结果只活在 `ModelsModule` 的
   `modelOptions` state 里，关掉设置面板就没了。用户每次打开设置、想选模型，都要重新点一次
   「拉取模型列表」并等一轮网络。
2. **流式失败不许丢内容，且能接着写** —— `courseChat.send` 的 `catch` 里，非 abort 的失败
   **只 `patchAi` 到内存、从不落库**（旧代码 `store/courseChat.ts:785-793`）。刷新页面那一轮
   就整段消失，用户看到的是「问过了，什么都没有」。
3. **对话消息要能重试 / 分支，Recent 也要能分支** —— 现在消息操作行只有
   「复制 / 复制纯文本 / 导出本次会话」，没有重来一次的入口。

顺带一个小的：Recent 标题超长时只能看省略号。

## 一、不变量（改动不能破坏的）

| # | 不变量 | 为什么 |
|---|---|---|
| 1 | `sessions` 的顺序永远是 `createdAt` 升序 | `bootstrap` 与 `deleteSessionById` 都拿 `sessions[sessions.length - 1]` 当「最新的那条」；一换序，默认选中的会话就跳到错的（既有约束，本轮不动） |
| 2 | 生成中（`loading`）不许切会话、不许删/归档、不许分支 | 库里还没有那条正在流的消息，切走再回来内容会被整段丢掉 |
| 3 | 脏历史允许留在库里，只在**请求边界**洗干净 | `api/messageHygiene.ts` 的分工，本轮新增的消息形态（续写前缀）同样走它 |
| 4 | 断点续传**只在库里已有那半条回答时**做 | 没落库就没有「断点」可言 —— 这正是需求 2 要先修的那件事 |

## 二、模型列表缓存

### 2.1 键为什么是 `baseUrl` 而不是 `provider.id`

`Provider.id` 由 `nextProviderId()` 顺序生成（`p1` / `p2` / …）。**删掉一家再加一家会复用
同一个 id**，于是「上一家的模型列表」会被当成新家的缓存命中 —— 用户在新家看到一屏别家的模型，
点下去就是 404。`baseUrl` 才是「这份列表从哪来」的真实身份。

键做归一化（trim + 去尾部斜杠）：`https://api.x.com/v1` 与 `https://api.x.com/v1/` 是同一家。

### 2.2 缓存里**不放** apiKey

apiKey 已经单独存在 settings 里（且明确不进云同步与迁移包）。把它复制进模型列表缓存等于
凭空多出一份凭据副本，而这份缓存的唯一用途是「省一次网络往返」，不值得。

代价说清楚：同一地址换 key 后（比如换成另一个账号），缓存里的列表可能与该 key 实际可见的
列表不同。所以**打开设置时只要缓存过期就会静默重拉**，TTL 取 24 小时；用户也可以随时点
「拉取模型列表」强制刷新。

### 2.3 三档行为

| 时机 | 行为 |
|---|---|
| 设置页打开 / 供应商增删改 | 先用缓存**同步**填上候选（不等网络），再对「无缓存或已过期」的家静默拉取 |
| 手动「拉取模型列表」 | 全部强制重拉，结果写回缓存，照旧出 toast |
| 删除供应商 | 顺手删掉它的缓存条目（否则条目只增不减，localStorage 迟早堆满） |

静默拉取失败**不弹 toast**：用户没主动要求，弹一条「拉取失败」只会制造焦虑，供应商那一行
的状态点已经说明了连通性（既有行为）。

## 三、失败不丢内容 + 断点续传

### 3.1 现状的问题不是「界面不显示」，是「没落库」

旧代码在非 abort 失败时把 `answer + 「> 回答中断：xxx」` patch 进内存消息，界面上**看得见**。
但那一轮没有 `db.chats.add` —— 刷新即消失，切会话再回来也没有。用户说的「任务一点都不显示」
就是这条路径。

### 3.2 落库，但**不把提示文案写进正文**

新增 `ChatRow.interrupted?: boolean` + `ChatRow.interruptReason?: string`（非索引字段，不升版本）。

**为什么不像停止那样把「（已停止生成）」嵌进正文**：续写要把这半条回答当 assistant 前缀
原样发给模型，正文里夹一句系统口吻的中文说明会污染它 —— 模型可能接着那句话往下写。
中断与否是**这条消息的元数据**，和 `reasoningMs` / `finish_reason` 同类，该单独存。

UI 上据 `interrupted` 渲染一条提示条（含原因）+ 一个「继续」按钮，正文保持干净。

`reasoning` 一并落库：思考到一半断掉时，用户最想看的就是它想了什么。

### 3.3 续写怎么做

「继续」触发 `retryMessage(key)`，走这条路径：

```
messages = [
  system,
  ...库里的历史（末尾就是那半条 assistant 回答）,
  { role: 'user', content: CONTINUE_INSTRUCTION },   // 「接着上面继续写，不要重复已写内容，不要重新开头」
]
```

三个取舍：

- **不重发那条 user 提问**。它已经在历史里，重发等于让模型把同一个问题看两遍。
- **续写不带 tools**（`tools: []`）。续写的语义是「把没写完的话写完」，此时再给它检索工具，
  它很可能放下笔去查资料 —— 那就不是续传了。
- **新内容追加到同一条消息**（`partial + delta`），而不是新开一个气泡。断点续传在用户眼里
  就是「一句话被接上了」，拆成两条读起来像两轮回答。

完成后 `db.chats.update(rowId, { content, reasoning, interrupted: undefined, interruptReason: undefined })`
—— **更新原行，不新增行**，所以历史里始终只有一条完整回答。

### 3.4 「重试」对**完整**回答是什么

`retryMessage` 按消息状态分流：

| 这条消息 | 行为 |
|---|---|
| `interrupted`（有半截内容） | **续写**（见 3.3） |
| 完整，且是**最后一条消息** | **重新生成**：删掉这条回答行，用它前面那条 user 提问重跑 |
| 完整，但不是最后一条 | 禁用。要从中间改，走「分支」——见第四节 |

为什么不做「删掉它后面所有消息再重跑」：那是一次不可见的批量删除，用户在 Recent 里看到的是
一条会话凭空少了一段。**要改历史中间的一步，正确动作是分支**，原会话不动、新会话可对比，
这是本轮同时做 fork 的原因。

### 3.5 停止生成那条**不动**

用户主动按停止时，照旧把 `（已停止生成）` 嵌进正文并落库（既有行为，`e2e-agent-guard` 有断言）。
理由：主动停止的人通常不想让它接着写；真要接着写，重问一次成本很低。
（写进「已知未做」，需要时可以补。）

## 四、重试 / 分支的语义与挂载

### 4.1 fork = 从某条消息分叉（用户确认的口径）

- **对话内**：以该消息为界，把它**之前（含它）**的消息复制成一条新会话，原会话完全不动。
- **侧栏 Recent**：等价于「从最后一条消息分叉」，即整条会话复制一份。

两条路径共用 `store/courseChat.ts` 的 `forkSession(sessionId, uptoRowId?)`。

**标题**：`${原标题} · 分支`。不另起一个「新会话」名字 —— 分支的用处就是「和原来那条比着看」，
标题里没有来源就认不出谁是谁。

**消息时间戳照抄原值**，不重新计时：`sortBy('createdAt')` 是稳定排序，复制的顺序按新 id 递增，
不会乱；而重打时间戳会让「这条会话是什么时候聊的」变成假数据。

### 4.2 挂在哪

| 位置 | 图标 |
|---|---|
| 助手消息 | 复制 · **重试** · **分支** · 更多（复制纯文本 / 导出） |
| 用户消息 | 复制 · **分支** |
| 侧栏 Recent 行尾菜单 | 重命名 · 置顶 · **分支** · 归档 · 删除 |

**重试不挂用户消息**：对一条已经发出去的提问，重试的唯一解释是「再发一遍」，而它没有可重试的
失败态（提问从不失败）。**分支挂两者**：从提问处分叉（换个问法再问）和从回答处分叉（沿着这个
方向往下走）都是真实需求。

菜单里「分支」排在归档之前：它**不是破坏性动作**，该离删除远一点。

### 4.3 禁用规则

- 消息还没落库（`rowId == null`，正在流式的那条）→ 两个图标都不出现。
- `loading` 中 → 分支禁用（不变量 2）；重试禁用。
- 完整但非最后一条 → 重试禁用（4.1 的第三条），tooltip 说明「用分支」。

## 五、Recent 标题 hover 跑马灯

`.course-chat` 之外，`ui/layout.tsx` 的 Recent 行标题从 `truncate` 改成：

```css
.recent-title { overflow: hidden; text-overflow: ellipsis; }
.recent-title > span { display: inline-block; white-space: nowrap; }
.recent-item[data-hovered='true'] .recent-title > span,
.recent-item:focus-within .recent-title > span {
  animation: recent-title-marquee var(--recent-duration, 5s) ease-in-out infinite alternate;
}
@keyframes recent-title-marquee {
  0%, 10% { transform: translateX(0); }
  90%, 100% { transform: translateX(var(--recent-shift, 0px)); }
}
```

要点：

- **hover（或键盘焦点）时才跑**，平时仍是省略号，不挂着滚动条 —— 常驻滚动条会让侧栏看起来像坏掉了。
- 位移量取决于内容宽度，CSS 算不出来，由 `layout.tsx` 的 `measureRecentTitles` 量好后
  写进 `--recent-shift`（负的溢出像素）与 `--recent-duration`（按约 40px/s 换算，长标题不滚得飞快）。
  没溢出时 `--recent-shift` 缺省 0，动画原地不动 —— 于是**只有超长标题会滚**。
- 两端各停 10%（`0%/10%` 与 `90%/100%`），进出都不唐突；`alternate` 让它在两端之间往复。
- 移开指针，动画撤掉、`transform` 回到 0，不会留下「中间一截 + 省略号」那副坏样子。
- `prefers-reduced-motion: reduce` 下停掉动画，退回省略号 + 重命名对话框看全文。
- **不用 `title` 属性**：iOS Safari 不显示原生 tooltip，而 iPad 是主力平台。
  触屏上的兜底是「重命名对话框里能看到全文」（已有能力）。

> 早期版本做的是「hover 变成可横向滚动的容器、手动去拨」，实测只对**触控板横滑**友好
> （普通鼠标滚轮的 `deltaY` 只滚外层列表），而且滑到一半移开会留半截标题。按反馈改成
> **跑马灯自动滚**。见 `e2e-chat-resume-fork.mjs` ⑫（量到溢出 / 动画挂上 / transform 真的左移 / 移开复位）。

### 7.1 e2e 脚本自身的三个缺陷（第一次真正跑绿时踩到，已修）

`scripts/e2e-chat-resume-fork.mjs` 此前**从未通过**。三个坑全在脚本里，**不在被测代码里** ——
记在这里是因为「测出来全红」很容易被误读成功能坏了：

1. **`reset()` 在导航之前就访问 IndexedDB。** `about:blank` 上 `indexedDB.open` 会被浏览器直接拒
   （`SecurityError: access to the Indexed Database API is denied in this context`）。
   修法有两步，缺一不可：先 `page.goto` 落到应用源上；再**等应用把库建好**
   ——裸 `open('wangke')` 拿到的是一个**没有任何 object store** 的空库，
   紧接着 `tx.objectStore('chats')` 就抛（Dexie 的表只在建库/升级时创建）。
2. **假流在 `enqueue` 之后立刻 `error()`。** Streams 规范里 `controller.error()` 会执行
   `ResetQueue`：**已入队但还没被读走的 chunk 会被一次性丢弃**。于是读取端一个字节都拿不到，
   测到的不是「流了一半断掉」，而是「一个都没流出来」—— 那走的是 `send` 里另一条分支
   （`error: true`，不落库），①②③ 因此全红，而根因根本不在被测代码里
   （界面上只剩一句「回答失败：boom: connection reset」）。
   修法：`error()` 之前等 50ms，让读取端把 chunk 消费掉，再断。
3. **`dbMessages` 把 `interrupted` 用 `!!` 收成布尔。** 续写完成的判据是「字段被 `delete`」，
   而 `!!undefined` 与 `!!false` 都是 `false` —— 一收就把「已清干净」和「没清干净」变成同一个值，
   ⑥ 那条 `assert.equal(…, undefined)` 永远不可能成立。修法：原样返回字段，不收布尔。

三者都写进脚本注释了，别再改回去。

### 7.2 全套里那 48 条失败与本轮无关

都能追到与本轮无关的既有原因，分三类：

| 类别 | 代表 | 现场 |
|---|---|---|
| 需要 `TEST_FILE`（测试视频）却没给 | `e2e-resume` / `e2e-import` / `e2e-mobile` / `e2e-player-enhance` / `e2e-comments` / `e2e-material-you` | 0.4~0.9s 内退出，连浏览器都没起来 |
| `mdui` → HeroUI 迁移留下的失效选择器 | `e2e-providers`（13 条全是 `fav-tab-*` / `serves-*` / `mdui-menu-item` 这类已不存在的 testid）、`e2e-mdui-adapter` | 30s 超时等一个永远不出现的节点 |
| 断言旧图标类名 | `test-quiz` | 断言 `mdui-sym-check`，而 `QuizCard.tsx` 已迁到 `Sym` |
| 编排环境（端口被别的进程占着 / 并发） | `e2e-storage-card` 在跑分里 0.9s 红，**单独跑 7 条全过** | 与脚本内容无关 |

判据是「本轮新增的两条测试都是绿的」，不是「全套是绿的」。

顺带修掉的两个**既有**缺陷（与本轮三个需求无关，只是同属对话页的输入框）：
`e2e-agent-guard.mjs` 与 `e2e-providers.mjs` 仍用着只认后代选择器的
`.course-chat__input textarea` —— 而 HeroUI 的 `TextArea` 把 `className` 落在 **textarea 元素本身**，
这条选择器一条都匹配不到（仓库里 `e2e-lazy-session` / `e2e-course-chat-cards` 早已记录过这个坑）。
补上 `textarea.course-chat__input` 那种形态后，`e2e-agent-guard` 的 **11 条失败全部转为通过**；
`e2e-providers` 仍红，但那些红是上表第二类（迁移留下的失效 testid）。

## 八、已知未做

1. **刷新后的续写**：刷新会杀掉整个 JS 上下文，续写要重建工具调用栈 —— 与「刷新后续跑」
   同一条理由不做。刷新后那条 `interrupted` 消息仍然**在**（这正是落库的意义），
   提示条与「继续」按钮照常可用，因为续写不需要重建任何循环状态。
2. **停止生成后的续写**：见 3.5。
3. **模型列表缓存的 ETag / 条件请求**：网关普遍不支持，且列表本来就小，24h TTL 够用。
