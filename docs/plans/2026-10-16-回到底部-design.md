# 对话页「回到底部」：粘底可以松手，松了才需要那颗按钮

日期：2026-10-16
状态：**已落地并验证**（`pages/CourseChat.tsx` / `pages/course-chat.css` / `ui/icons.tsx` / `utils/motion.ts`；测试 `scripts/e2e-chat-scroll-bottom.mjs`）
实测：`tsc -b` ✅ · `vite build` ✅ · `e2e-chat-scroll-bottom` 7/7 ✅
范围：**只做「AI 助手」页**（`pages/CourseChat.tsx`）。播放页问答面板（`components/ChatPanel.tsx`）不在本次范围（见 §四）。

## 背景与目标

需求是一句话：**在 chat 栏加一颗「回到底部」的图标**。但这句话背后藏着现有实现的一个坑：

原来的自动滚动是**写死的**——只要消息内容变了（`scrollSignal` 一变），就无条件

```ts
element.scrollTop = element.scrollHeight;
```

也就是说**用户根本没有「滚上去读历史」这个状态**：流式回答每来一个 token 就把视图拽回底部，
往上翻看前文时刚读两行就被甩回去。一颗「回到底部」的按钮在这种前提下一个都用不上
（永远在底部，按钮永远不出现）。

所以这不是「加一颗按钮」，而是**先把「要不要跟到底」这件事交给用户**，再给他一个回来的入口。

目标：

1. 消息流默认粘底：新内容自动跟到底，什么都不用点；
2. **用户一旦自己往上滚就松手**——之后新内容不再动他，视图停在原处；
3. 松手（离底部）时，输入卡正上方浮出一颗向下箭头按钮；
4. 点它平滑回到最新，回到贴底后按钮收起。

## 一、方案

三块改动，都很小：

| 位置 | 改动 |
|---|---|
| `ui/icons.tsx` | 新增图标名 `arrow_downward`（`ArrowDown`），与发送用的 `arrow_upward` 成对 |
| `utils/motion.ts` | **新增**。把 `prefersReducedMotion()` 从 `components/mermaid/drawMark.ts` 提到公用处——它不属于 mermaid，「回到底部」是第二个消费者 |
| `pages/CourseChat.tsx` | `stickRef`（还粘不粘底）/ `jumpBtnRef`（按钮）/ 滚动监听 / 切会话复位 / `jumpToLatest` |
| `pages/course-chat.css` | `.course-chat__scroll-bottom`（按钮外观与显隐过渡），`.course-chat__composer-wrap` 加 `position: relative` 当锚点 |

按钮挂在 `.course-chat__composer-wrap` 里，用 `bottom: calc(100% + 10px)` 停在**整块输入区正上方**。
锚在输入区而不是消息区、也不是 `.course-chat__main`：队列条一出现输入区就变高，锚在 main 上
按钮会被压进输入卡里；锚在消息区则按钮会跟着消息一起滚走（`overflow: auto` 的容器里
`position: absolute` 的子元素是随内容滚的）。

水平居中用 `left: 0; right: 0; margin: 0 auto`，**不用 `transform: translateX(-50%)`**——
`transform` 要留给入场动画（淡出时往下错开 8px），两者抢同一个属性会打架。

## 二、两个关键判断（都踩过坑）

### 1. 显隐写 `data-show`，不挂 state

按钮显隐每滚一下都在变。挂 `setState` 等于整棵消息树（每条消息都要重渲 Markdown）跟着重渲——
这是 `ReasoningChain` 早就踩过的坑，它用 `el.dataset.fadeBottom` 解决。这里照抄：
**JSX 里压根不声明 `data-show`**，滚动回调直接写 `jumpBtnRef.current.dataset.show`。
不声明这个属性是有意的——React 会（在自身重渲时）覆盖它管理的属性，完全不管才不会被抹掉。

### 2. 「粘不粘底」按**方向**判，不能按「离底部多远」

第一版写的是最常见的那个判据：

```ts
const atBottom = distance <= NEAR_BOTTOM_PX; // distance = scrollHeight - clientHeight - scrollTop
```

探针直接把它打回来了：流到一半视图就停在半空，`scrollTop` 只有 38。根因是**竞态**——
流式追加时内容一帧能长几十像素，我们自己那次吸底滚动的事件要等到事件循环稍后才派发，
那一刻 `scrollHeight` 已经又长了一截，「离底部 > 24px」照样成立 → 每来一个 token 都误判成
「用户滚上去了」→ 粘底立刻松手。

真正说明用户**主动往上滚**的只有一件事：`scrollTop` 变小了。
（我们自己的吸底只会把它推到最大；内容增长压根不动 `scrollTop`。）所以：

```ts
if (distance <= NEAR_BOTTOM_PX) stickRef.current = true;        // 到了底部，重新粘上
else if (top < lastTopRef.current - 1) stickRef.current = false; // 只有「上滚」才松手
```

`NEAR_BOTTOM_PX = 24` 与 `ReasoningChain` 判「用户滚没滚」用的是同一把尺，两处的「贴底」不各算各的。

## 三、验证

`scripts/e2e-chat-scroll-bottom.mjs`（不花 API），7 条覆盖：

1. 打开会话自动落到底部（可滚范围 > 200px 且距底 ≤ 24px）；
2. 贴底时按钮隐藏；
3. 往上滚 → 按钮浮出（等到 `opacity` 真的走到 1，而不是刚 `visibility` 翻面）；
4. 滚回底部 → 按钮又隐藏；
5. 滚动后点按钮 → 平滑回到底部并再次隐藏；
6. `prefers-reduced-motion`：点按钮仍然到位（只是不平滑）；
7. **滚上去后追加流式内容 → 视图留在原处、按钮保持可见**（本轮改动的核心）。

前几条把一条写好的长回答直接种进 IndexedDB（渲染层，快且稳，取舍同 `e2e-chat-sources`）；
第 5 条之后需要一次**真实的内容增长**，所以那一段用页内假模型流（`addInitScript` 换 `window.fetch`）。

> 测试里的显隐断言一律等**计算后的 `visibility`**，不能只等 `data-show`：
> `visibility` 是跟着 150ms 过渡走的（收起时它必须撑到淡出结束才翻成 `hidden`，
> 否则按钮会在淡出中途突然消失），`data-show` 一变就读计算值会读到上一态。

## 四、不做的

- **播放页问答面板（`ChatPanel.tsx`）不加**：用户明确只要对话页。它的消息流结构、滚动容器
  （`PanelBody`）都不一样，要加得单独走一遍（同样的两句判断可以照搬）。
- **不做未读计数徽标**：流式期间「新内容」是**同一条回答在长高**，不是新消息，
  「N 条未读」在这个语义下是编不出来的数。松手后按钮本来就一直可见，不需要再拿徽标提醒。
- **不做「滚到底部时也常驻半透明」**：贴底时它没有任何可点的动作，常驻只会白占一块最容易读到的位置。
