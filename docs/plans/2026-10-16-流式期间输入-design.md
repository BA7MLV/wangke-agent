# 流式期间的输入：排队与插入设计

日期：2026-10-16
状态：**已落地并验证**（`store/courseChat.ts` / `pages/CourseChat.tsx` / `pages/course-chat.css` / `ui/icons.tsx`；测试 `scripts/test-chat-followup.mjs`、`scripts/e2e-chat-followup.mjs`）
实测：`tsc -b` ✅ · `vite build` ✅ · `test-chat-followup` 7/7 ✅ · `e2e-chat-followup` 7/7 ✅（单独跑与全套跑分里各一次，两轮全绿）

## 背景与目标

这一版之前，「AI 助手」页在生成期间是这副样子：

- 输入框 `disabled={loading && pendingAsk == null}` —— **想打一个字都打不进去**；
- 工具行上发送键**变成**停止键 —— 两颗按钮二选一。

于是「等它答完，接着问下一句」这个最自然的动作没有入口：想补一句话，只能先按停止，
而停止会把这一轮**已经写了一半的回答作废**（落库时标 `（已停止生成）`）。
用户真正的意图往往只是「别打断，让我把下一条排上」。

目标：流式期间**输入全程可用**，投递分两条路，按业界既有实践做：

| 产品 | 做法 |
|---|---|
| Codex CLI | 生成中说话 = steer（打断）/ Tab 排队，Enter 与 Tab 分工明确 |
| Claude Code | 消息排队，本轮答完自动发；取消一次运行**不会**丢掉排在后面的补充 |

口径由用户拍板：**只做「AI 助手」页**（`pages/CourseChat.tsx` + `store/courseChat.ts`），
**默认排队**（不打断是更安全的默认值，插入是显式选择）。

非目标：

- **不做问答面板**（`components/ChatPanel.tsx`）：那边挂在播放页、形态与工具条都不同，
  同一套逻辑照搬会引入第二份队列实现。要做先抽共享 hook，本轮不做。
- **不做桌面 Codex 那套可拖拽排序的队列**（理由见 §四）。
- **不做刷新后续跑**：刷新杀掉整个 JS 上下文，与「流式续传」同一理由（见那份设计 §八）。

## 一、不变量（改动不能破坏的）

三条，写在 `store/courseChat.ts` 文件头，与排队条的三条设计一一对应：

| # | 不变量 | 为什么 |
|---|---|---|
| 1 | **消息永远不会静默丢失** | 插入投不进去时（abort 之后发现新一轮已经跑起来了）一律降级成排队；队列本身逐条可编辑 / 删除 / 立即发送 |
| 2 | **`pendingAsk` 优先于两种模式** | 提问卡悬着时用户打的字是**对那张卡的回答**，那时循环在等用户、不是「正在生成」；排队或插入插一脚会有两条消息同时挤进同一个会话 |
| 3 | **队列只活在内存里，不落库** | 它是「还没交出去的话」，不是历史。真正的持久化发生在它被 `send` 出去那一刻（那一刻起它就是一条普通 user 消息） |

## 二、两条投递路径

### 2.1 语义与按键

| 模式 | 语义 | 代价 |
|---|---|---|
| `queue` **排队**（默认） | 挂到队尾，**这一轮答完自动接着发** | 不用等、不打断；这话要到下一轮才生效 |
| `steer` **插入** | 立刻 abort 当前这一轮，把它当成新一轮的提问 | 立刻改口；当前这轮到此为止（**已写出的部分留着**） |

按键（`pages/CourseChat.tsx` 输入框 `onKeyDown`）：

- **Enter = 当前模式**（默认排队）；
- **Ctrl/⌘+Enter = 另一种**（与 Codex 的 Enter/Tab 同构：两者都是「这一次怎么发」，
  不改默认值）。

默认值由工具行上的切换钮管（`sendMode`，见 §三）。没在生成中时 `mode` 传什么都一样
（`send` 直接发），所以按键处理不需要再判一次 `loading`。

### 2.2 `send` 的分流头

旧实现在 `loading` 时直接 `return` —— 用户打了字、按了回车、什么都没发生。
现在这里是分流点（`store/courseChat.ts:648-659`）：

```
pendingAsk      → answerAsk（不变量 2，优先）
loading         → draft 清空 + 按 mode ?? sendMode 走 steer / enqueue
其余            → 正常发一轮
```

草稿先清空：话已经交出去了，不管进队列还是新一轮 —— 不清的话队列里多一条、
输入框里还留着原文，用户会以为没生效而再打一遍。

### 2.3 `steer` 的时序（为什么必须等 `inflightDone`）

```
turn.intent = 'steer'      // 告诉 finally：这次 abort 是插入，不是停止
turn.abort.abort()
await inflightDone         // 等这一轮收尾（落库写完、loading 置回）
if (loading) → enqueue     // 等收尾的几百毫秒里又有人插了一条 → 降级排队，不丢
else → send(text)
```

三步各有各的理由：

- **`intent` 先置位再 abort**：`finally` 靠它区分「停止」与「插入」的落库痕迹
  （见 2.4）。顺序反了的话 abort 可能已经触发收尾，看到的还是旧 intent。
- **必须等收尾**：不等的话下面那次 `send` 会被自己的分发逻辑当成「生成中」，
  于是插入变成排队 —— 反了。`endInflight` 只 resolve 一个 promise，等它的人要等
  当前同步块跑完才轮到，所以 `steer` 醒来时看到的必然已经是 `loading: false`。
- **醒来再判一次 `loading`**：这几百毫秒的窗口里用户可能又插了一条（新一轮已经在跑），
  这条就**降级成排队** —— 不变量 1 的落点。两条插入撞车的竞态由 store 测试 D 守。

### 2.4 落库痕迹：`AbortIntent = 'stop' | 'steer'`

中断原因写进 `interruptReason`（元数据字段，不污染正文 —— 与「流式续传」那份设计
§3.2 同一条理由：续写要把这半条回答当 assistant 前缀原样发给模型）：

| 打断方式 | 正文 | 元数据 |
|---|---|---|
| 用户按停止 | 追加 `（已停止生成）` | 无（既有行为，`e2e-agent-guard` 有断言） |
| 插入 | **半截原样保留** | `interrupted: true` + `interruptReason: '你发了一条新消息，这一轮先停下来'` |

文案说「你发了一条新消息」而不是「被新消息打断」：用户看到它时，那条新消息就在下面 ——
两句话能对上。而且插入留下的半截**可续写**（提示条 + 「继续」按钮，复用上一轮的机制）。

### 2.5 `drainQueue`：本轮一结束就发队首

挂在每轮的 `finally`（`store/courseChat.ts:1131-1137`），三道前置
（`loading` / `!loaded` / `pendingAsk`）缺一不可。

**被停止打断也发**：这是刻意的，与 Claude Code 一致 —— 「取消一次运行不会把已经排在
后面的补充说明一起丢掉」。用户真想让整个队列停下，排队条上有「清空」。

⚠️ **先出队再 send**：`send` 是异步的，留着那条在队里会让下一轮的 `finally` 再送一次
（同一个问题被问两遍）。出队与发送之间没有 `await`，所以这条不会被别的路径插队。

## 三、模式切换与「发送键常驻」

### 3.1 发送键与停止键**并存**，不再二选一

旧逻辑「生成中发送键变成停止键」把两个不同的问题绑成了一颗按钮：

- 「这话怎么发」（发送）与「别写了」（停止）回答的不是同一件事；
- 绑在一起的代价：想补一句话只能先按停止，而停止作废这轮已写出的半截。

现在两颗并排：发送键 tooltip 随模式变文案（「排队发送：等这一轮答完自动发出去」/
「插入发送：立刻打断这一轮，换成这句」），停止键照旧只断请求、保留已流出内容。
有提问卡悬着时停止键隐藏（那时循环在等用户答卡，没有「正在生成」可停）。

### 3.2 模式切换钮只在生成中出现

`ToggleButtonGroup`（HeroUI v3 + RAC，`selectionMode="single"` + `disallowEmptySelection`），
「排队 / 插入」两颗，挂在工具行设置组里、紧挨破坏性动作之前 —— 离发送键最近的一颗设置。

**不生成时它没有意义**（那时发出去就是立刻发），常驻只会白占一行。
⚠️ 它自己也是 RAC Toolbar（`useToolbar`），`onKeyDown` 会 stopPropagation ——
方向键在档位里换档、不会把焦点甩出这一行。嵌套是安全的，别拆。

### 3.3 提示行说清按键

`composerNote` 在生成中改说当前模式（「Enter 排队，答完这轮自动发下一条 ·
Ctrl/⌘+Enter 立刻插入并打断 · 已排 N 条」），其余时候保持原来的免责声明 ——
别在非生成期占着这行说按键。tooltip 要 hover 才看得见，而按键知识是这一时期
唯一需要记住的东西。

## 四、排队条

渲染在输入卡**正上方**（`.course-chat__queue`）：它和输入框是同一件事的两种状态
（「已经排上的」与「正在打的」），分居两地会让用户以为队列是另一个功能区。

四个操作，三条设计：

| 操作 | 实现 | 理由 |
|---|---|---|
| **逐条编辑** | `Input` + `updateQueued`；改成空白 = 删掉 | 排队那几秒里用户常常后悔，能改就不必删了重打。留一条永远发不出去的空气泡没有意义 |
| **立刻插入这条**（闪电键） | `sendQueuedNow`：先出队再 `steer` | 想提前说一条就说一条，所以**不需要拖拽排序** —— 桌面 Codex 那套可拖拽队列在这里是过度设计 |
| **删掉这条** | `removeQueued` | |
| **清空**（右上角） | `clearQueue` | 停止生成之后想彻底收手时用 |

图标：`schedule`（排队意象，Lucide `Clock`）与 `bolt`（插入 / 立刻投递，Lucide `Zap`）
加进 `ui/icons.tsx` 映射 —— `schedule` 是绕开与 toc / quiz 撞车后的选择。

## 五、流式尾巴：黑色圆形

### 5.1 落点是 XMarkdown 的 `tail.component`

```tsx
streaming={{
  hasNextChunk: !!message.streaming,
  tail: message.streaming ? { component: StreamTailCircle } : false,
}}
```

`<xmd-tail>` 被注入 markdown AST 的**最后一个文本 token 之后**（XMarkdown Parser 的
`configureTailInjection`）—— 也就是**下一个字符将出现的位置**。圆点跟着文字一起长，
眼睛不用去屏幕底部找「生成到哪了」。`shouldShowTail = !!hasNextChunk && tailContent`，
写完即消失。

比自造兄弟元素正规：自己算「最后一个 token 在哪」就要重新实现一遍 markdown 遍历。

### 5.2 为什么是圆点

- **不是默认方块 `▋`**：它与文字笔画一样重，长文本里会读成一个错字；
- **不是竖线**：终端传统，这个产品里没有对应物；
- **圆点轻一档**，闪一闪只表示「这儿还在写」，不假装自己是内容。

### 5.3 颜色与动效

```css
.course-chat__stream-dot {
  display: inline-block; width: 0.5em; height: 0.5em;
  margin-left: 0.12em; border-radius: 50%;
  background: var(--foreground); vertical-align: 0.08em;
  animation: course-chat-dot-blink 1.1s ease-in-out infinite;
}
```

- 颜色取 `--foreground`：浅色主题下它就是 `--eclipse`（近黑，`oklch(21.03% .0059 285.89)`），
  正是用户要的「黑色圆形」；深色主题里死黑会看不见，而「跟文字同色的指示符」在任何主题都成立。
- `prefers-reduced-motion: reduce` 时关掉闪烁（圆点本身仍在）。
- 尺寸用 `em`：跟着正文字号缩放，长文里不会变成一个突兀的坨。

### 7.1 测试台自身的坑（第一次跑时踩到，已修）

1. **假流必须接 `init.signal`**（`e2e-chat-followup.mjs`）。不接的话 abort 无法让读取端
   收手，假流自顾自吐完 —— 症状是「按了插入，旧回答还在继续写」，被测代码明明是对的，
   红的却是测试。做法同 `e2e-agent-guard.mjs`：abort 时直接 `error` 掉这条流。
2. **「本轮结束后排队该自动发出请求」要等 fetch，不能等上屏**（`users===2` 上屏与
   fetch 发出之间有几十毫秒缝：`send` 同步上屏消息、之后还有 await 才 fetch）。
   断言改成等 `calls` 增长。
3. **插入用例的基准要抓在插入前一刻**。抓在「第三个问题」之前的话，等 `users +1`
   会在 steer 推到 `+2` 后永远为假。
4. **沙箱 Chromium 访问 `localhost:4173` 不通、`127.0.0.1` 通**。跑这个脚本
   `BASE_URL` 必须写 `http://127.0.0.1:4173`。
5. **模式切换钮只在生成中渲染**。⑤ 号用例结尾「切回排队模式」的点击发生在空闲时，
   干等 30s 超时，且 `sendMode` 残留 `steer` 污染后续用例。修法：把切回排名的点击
   移到慢流进行中。

### 7.2 既有 e2e 不受影响

`e2e-agent-guard` 对「停止键」「输入框禁用」的断言在新行为下仍成立 ——
`chat-stop` testid 保留、禁用条件从「生成中」改成「历史未就绪」后该脚本的场景照旧通过
（上一轮 11 条失败源于选择器不认 HeroUI 的 className 落点，与本次行为变更无关）。

## 八、已知未做

1. **问答面板（ChatPanel）的同一套能力**：见「非目标」。要做先抽共享 hook。
2. **拖拽排序**：排队条给的是「闪电键」这种更轻的插队方式；拖拽在触屏上还要另做一套
   长按手柄，收益不抵复杂度。
3. **刷新后的队列**：队列不落库（不变量 3），刷新即空。这是刻意选的 ——
   「刷新时以哪份为准」的问题不值得为「省一次重打」引入。
4. **`steer` 的二次确认**：插入会作废当前这轮（半截留着），目前靠 tooltip 与提示行
   说清代价，不弹确认。作废的半截可续写，误插入的代价没有高到需要一道确认。
